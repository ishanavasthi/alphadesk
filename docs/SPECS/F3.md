# F3 — Per-user broker linking

Branch: `v2-foundation` (off `main` @ `e62af64`, after F2).

Before this card, AlphaDesk held **one** IND Money credential for the whole
process — a module-level `_Auth` singleton in `backend/tools/ind_money_auth.py`,
hydrated from `backend/.ind_money_token.json`. Whoever pressed Connect linked
*the server*; every other visitor's `/portfolio/*` request read that person's
holdings. C0 papered over it with a shared admin secret, which is the correct
thing to do to a hole you cannot yet close and the wrong thing to leave.

This card closes it. The credential becomes one Fernet-encrypted `broker_links`
row per user, the OAuth `state` becomes a row that names its owner, and the C0
admin gate is replaced by a verified Clerk identity everywhere except one
clearly-marked interim path that dies at L1.

---

## 1. `AuthStore.for_user(user_id, source)`

```python
from tools.ind_money_auth import AuthStore

store = AuthStore.for_user(user_id)      # source defaults to "ind_money"
token = await store.get_token()          # refreshes if expired
status = await store.status_verified()   # truthful, and it says why
```

| | before | after |
|---|---|---|
| where the tokens live | `backend/.ind_money_token.json` | `broker_links.{access,refresh}_token_enc` (Fernet) |
| who they belong to | the process | one `user_id` |
| the lock | one `asyncio.Lock` for everybody | one per `(user_id, source)` |
| the client secret | plaintext in a JSON file | `client_secret_enc` |

**The refresh and expiry logic is carried over verbatim.** `status_verified()`
and `_refresh_token()` were correct — a live token short-circuits with no
network call, an expired one is *actually* refreshed rather than assumed good, a
4xx is definitive and a 5xx is transient. Only their scope was wrong. The one
addition is described in §7.

**Locks are keyed, not global.** A refresh is a network round-trip to the
broker; a single lock would have made every user in the process wait behind the
slowest one. `_lock_for((user_id, source))` hands out one lock each, and a test
proves user B's token comes back while user A is still parked inside their own.

**Stores are cached per user, and bounded.** `AuthStore.for_user` returns the
same instance so a hydrated credential (and the memory that the source
definitively rejected it) survives between requests instead of costing a DB read
plus a Fernet decrypt on every MCP call. The cache is capped at
`_CACHE_MAX = 1000` and dropped wholesale on overflow, together with the lock
table: these hold **decrypted** tokens, so an unbounded cache is not merely a
leak but a growing pile of plaintext credentials in a long-lived process — and
it would also keep serving a `"local"` store that adoption has since moved out
from under. Locks and stores are evicted together; a lock kept without its store
protects nothing, and a lock dropped while its store lives on would let two
refreshes race.

### A link row the server cannot decrypt

`TOKEN_ENCRYPTION_KEY` is an environment variable on a Space that anyone with
access can edit, so "the key moved and every stored credential is now
unreadable" is an operational state, not a hypothetical. It used to escape as a
bare `TokenEncryptionError` — a `RuntimeError` — from `/auth/status`,
`/auth/login`, `/auth/logout` and every `/portfolio/*` route, i.e. a **500**.

It is not a 500. The link is intact at the source and the request is fine; we
simply cannot read what we stored, and re-linking fixes it. So `_hydrate_from_row`
catches it and marks the store `undecryptable`: `link_health` answers
`NEEDS_RELINK` (never `REVOKED` — nobody revoked anything), the status payload
carries `undecryptable: true`, and the row is **left alone** so restoring the old
key restores the link. A server with no key at all refuses to link at
`/auth/login`, in words, rather than after the user has been round-tripped
through the broker and spent a one-use code.

### Single-tenant dev, unchanged

`ALPHADESK_SINGLE_TENANT=1` is the operator's own machine. It is now the **only**
mode in which any ambient credential source is read at all — the static
`IND_MONEY_MCP_TOKEN`, the `IND_MONEY_OAUTH_*` triple, the Claude Code
credential store, and the on-disk cache file. And even then only for
`user_id="local"`: `_is_local_dev()` requires both halves, so the flag is not a
licence to serve the operator's file cache to a real Clerk user who happens to
be asking on the same process.

With the flag unset, none of them authenticates anybody. That is the security
fix stated as one sentence, and there is a test that sets up all four sources
and asserts both `"local"` and a Clerk id come back unauthenticated.

Local dev with **no** Postgres keeps working: hydration falls back to the file,
`_persist` mirrors to it, and the pending-state row lives in a process dict
(`_pending_in_memory()` requires single-tenant mode *and* an unset
`DATABASE_URL`, so it is unreachable on any deployment).

## 2. OAuth state is a row, and the row names its owner

`_PENDING: dict[str, dict]` is gone. `POST /auth/login` writes an `oauth_pending`
row — `state → user_id`, plus the PKCE verifier, the redirect URI, and the
client credentials with the secret encrypted — **before** it hands the
authorization URL out.

`GET /auth/callback` then resolves the owner from `state` **alone**. Not a
cookie, not a header, not a query parameter beyond the OAuth ones. The request
that lands there is a redirect from the broker, and everything a redirect
carries about identity is attacker-choosable.

Two rules, both enforced on read:

- **Single use.** The read and the delete are one statement — `DELETE FROM
  oauth_pending WHERE state = :s RETURNING …`. A SELECT-then-DELETE would let
  two callbacks racing on one state both see a row, and the entire point is that
  the second one loses.
- **Ten-minute TTL** (`STATE_TTL_SECONDS`). Longer than any honest login, short
  enough that a leaked authorization URL is worthless by the time it is found.

Either failure renders a plain error page saying so, and links nothing.
`purge_expired_pending()` exists for housekeeping, not for security: expiry is
enforced on read, so a leftover row is already inert.

## 3. Scopes, and the client that gets reused

**Both scopes are requested**: `portfolio:read market:read`. C2 verified
`scopes_supported` is exactly those two (`docs/ind_money_payloads.md` §Q5), and
discovering later that the missing one was needed costs a full re-link.
Overridable via `IND_MONEY_OAUTH_SCOPE`.

**The registered client is stored and reused.** C2 established that per-user
dynamic client registration is viable — the pre-F3 code registered a fresh
confidential client on *every single login* and those clients completed the full
exchange in production. F3 keeps the plan default and stops the churn: the
`client_id` and encrypted `client_secret` live on the link row, and a re-link
reuses them.

A new registration happens in three cases: there is no stored client, the stored
one was registered against a **different redirect URI**, or the server
**rejected** it.

The second case is why migration `0004` adds `broker_links.redirect_uri` — DCR
binds a client to its `redirect_uris`, so a deploy that moves the backend origin
silently invalidates every stored client, and without the column the only way to
discover that is by watching a user's login fail.

The third is the recovery half of reuse, and it is the failure mode a real
morning re-login is most likely to hit. A token-endpoint response of
`invalid_client` / `unauthorized_client` (or a bare 401, which RFC 6749 defines
as a client-authentication failure) means the registration itself is dead —
deleted, rotated, expired. Without recovery, the same dead `client_id` is loaded
from the row on every attempt and *every* login and refresh fails identically
forever, with no way out but editing the database.
`AuthStore.forget_client()` nulls `client_id` / `client_secret_enc` /
`redirect_uri` so the next press of Connect registers a new one. It deliberately
does **not** touch the tokens: a rejected client says nothing about whether the
refresh token is still good. `invalid_grant` — the ordinary expired-token case —
leaves the registration alone, which a test pins in both directions.

## 4. Unlink revokes, then deletes

`POST /auth/logout` calls the discovery document's `revocation_endpoint` for the
refresh token **before** deleting the row. Deleting our copy and calling it a
disconnect leaves a live grant on the broker's side that the user cannot see or
reach; "we forgot your token" is not "your access is gone".

An upstream failure still deletes locally — the user asked to be unlinked and
refusing would strand them — but the response says so:

```json
{"authenticated": false, "revoked_upstream": false, "revocation_error": "…"}
```

Scope note, from C2: RFC 7009 revocation kills **tokens**, not client
*registrations*, and this server exposes no client-deletion path. The client
credentials go with the link row locally; the registration itself persists on
the vendor's side. That is the known volume risk C2 flagged, unchanged.

## 5. Which credential opens which door

| endpoint | Clerk JWT | C0 admin header | anonymous |
|---|---|---|---|
| `POST /auth/login` | ✅ | ❌ 401 | ❌ 401 (except single-tenant dev) |
| `POST /auth/logout` | ✅ | ❌ 401 | ❌ 401 (except single-tenant dev) |
| `GET /auth/status` | ✅ the caller | ✅ the operator *(interim, ledgered)* | "not connected", named for nobody |
| `GET /auth/callback` | — | — | the `state` is the credential |
| `/portfolio/*` (5 routes) | ✅ | ✅ **interim** | ❌ 401 |
| `/internal/*` | — | — | `CRON_SECRET`, unchanged |

**Linking is JWT-only.** An admin-header link would be a link with no owner,
which is the precise shape of the process-wide credential this card deleted —
and the thing C0 was invented to stop. The frontend does not even send the
header to those two endpoints any more.

**`/auth/status` no longer answers for the process.** It used to tell anyone on
the internet whether the operator was connected. Now it answers for the caller,
and an anonymous caller gets a flat "not connected" rather than a truthful
readout of somebody else's link.

### The interim admin path, and how to delete it

`NEXT_PUBLIC_AUTH_ENABLED` is **off** in production until card L1, so the
deployed frontend has no sign-in UI and can mint no Clerk token. A pure-JWT gate
on `/portfolio/*` would therefore lock the operator out of their own dashboard
for the entire interval between this card and that release. So those routes
accept **either** credential, and a JWT always wins when one is present.

`/auth/status` accepts it too, and that is a deliberate exception to "`/auth/*`
is JWT-only" rather than an oversight: it is a *read*, and the flag-off v1
research page polls it with no session. Writing a link under a shared secret is
what stays forbidden, because a link written that way has no owner.

**There is exactly one acceptance rule**, `api.main.admin_secret_accepted()`.
Every site calls it. The first version of this card had grown a third,
inline copy inside `_status_identity` that no removal note mentioned — which is
precisely how an interim gate outlives the release meant to delete it.

#### L1 removal checklist — every site, none of them optional

| # | Where | What |
|---|---|---|
| 1 | `backend/api/main.py` | `admin_secret_accepted()` — the one rule |
| 2 | `backend/api/main.py` | `_require_admin()` — the raising wrapper |
| 3 | `backend/api/main.py` | the admin branch of `_status_identity()` (`/auth/status`) |
| 4 | `backend/api/routes/portfolio.py` | `_admin_identity()` |
| 5 | `backend/api/routes/portfolio.py` | the `x_alphadesk_admin_secret` parameter of `portfolio_identity()` |
| 6 | `backend/services/adoption.py` | `admin_identity()` — only this path uses it |
| 7 | `frontend/lib/api.ts` | `ADMIN_SECRET` and the three headers it sets |
| 8 | HF Space | unset `ALPHADESK_ADMIN_SECRET` |

Step 8 alone already fails all of 1–6 closed, because `admin_secret_accepted`
returns False with no secret configured — a test pins that every site goes shut
together. The other steps delete the code.

A *bad* token never falls through to the admin path. Presenting a rejected token
alongside a valid admin secret is a 401, because otherwise the effective
credential is whichever of the two is weaker and every future tightening of the
token path is decorative.

An admin-header request acts as the operator's identity: their Clerk id once
they have signed in (adoption has moved the data there), `"local"` before that
(the data is still there). Never a stranger, and never "the only user in the
table" — see `services.adoption.admin_identity`.

## 6. Adopting the pre-F3 `"local"` data

Everything stored before identity existed is keyed on `user_id="local"`: the
operator's broker link, and every daily snapshot card S1 has captured. The
source is point-in-time, so **a lost snapshot day cannot be recovered**. Turning
identity on without moving those rows would orphan the history behind an id
nobody can sign in as.

`services/adoption.py` moves them, under one rule:

> Adoption runs only for the person named in `ALPHADESK_OPERATOR_EMAIL`, matched
> against their **verified primary** email address.

Not "the first user to sign in". On a public deployment a first-comer rule hands
one stranger the operator's entire net-worth history, and the class of mistake
this card exists to fix is exactly that one. With the variable unset, adoption
never runs at all.

**Where the email comes from: Clerk, always.** The token's `email` claim is used
for one thing — a cheap **negative** pre-filter. A claim that disagrees with the
operator's address ends the check with no network call; a claim that *agrees*
proves nothing and is still confirmed against the Clerk Backend API.

That asymmetry is the security property, and the first version of this card got
it wrong: it returned the claim unconditionally when one was present. `claim_email`
reads whatever `email`-ish claim an instance's JWT template emits, and a template
can be configured to emit an address its owner typed and never verified — so
anyone able to put `operator@…` in their own token would have inherited the
operator's links and snapshots, *and* become `operator_user_id()`, which is also
the ambient identity and the identity every interim admin-header request acts
as. Only the **primary** address counts, and only if
`verification.status == "verified"`.

The consequence is that adoption needs `CLERK_SECRET_KEY`. Without it, nothing
is adopted: no adoption is recoverable (set the key, sign in again), a wrong
adoption is not.

**Only a settled answer is remembered.** `maybe_adopt` runs on every
authenticated request until a user has an answer, and caches "not the operator"
so a non-operator does not cost a Clerk lookup per request. It caches *only*
that. A Clerk outage, a 5xx, or a missing secret key leaves the cache untouched
and is retried — otherwise one bad minute during the operator's first sign-in
would strand their entire snapshot history behind `"local"` for the life of a
process that can stay up for weeks.

**`operator_user_id()` matches with `lower(email) = …`, not `ILIKE`.** LIKE
treats `%` and `_` as wildcards and `_` is legal in an email local part, so an
`ALPHADESK_OPERATOR_EMAIL` of `ops_admin@example.com` would also have matched a
signed-up `opsXadmin@example.com` — a stranger promoted to operator by a
character nobody thought was special.

**Idempotent by construction.** Adoption moves rows *off* `"local"`; a second
pass finds nothing to move. Rows that would collide with something the target
user already has (same broker source, same captured day) are left behind rather
than overwritten — the signed-in user's own data always wins.
`snapshot_holdings` and `snapshot_raw` hang off `snapshot_days.id` and move with
their parent untouched.

It runs from `deps.register_identity`, which **every** authenticated entry point
goes through. That is not tidiness: the live run of this card found adoption
silently never firing because `/auth/status` — the first call a freshly
signed-in browser makes — was reading the token without registering the user.

## 7. Per-user connector, and the REVOKED carry

`IndMoneyConnector` is bound to a user's `AuthStore` rather than to a
process-wide token. `get_connector(user_id)` **takes the user id**; the pre-F3
signature took nothing and returned the one connector the process had, which is
how a single credential ended up answering for everybody. Any new call site that
cannot name a user is a call site that should not be reading holdings.

Connectors are still cached per user (bounded at 1000, dropped wholesale on
overflow) because the instance remembers that the source definitively revoked
*that user's* grant, and re-learning that costs a doomed call.

The nightly job builds one connector per linked user:
`capture_all(session, connector_factory=get_connector)` over
`capture_users(session)`, which selects `DISTINCT broker_links.user_id` and
falls back to `["local"]` only while the operator's row is still keyed that way.

**The M1/S1 carry.** `status_verified()` catches `MCPAuthInvalid` internally —
it has to, or an idle status poll would raise — and used to flatten it into a
plain `authenticated: False`. So a definitively dead grant was reported as the
softer `NEEDS_RELINK` forever, and `LinkHealth.REVOKED` was unreachable on an
idle poll. The status dict now carries `revoked: bool`, the link row's `status`
column is set to `"revoked"`, and `link_health()` reads it. A 5xx still reports
"not authenticated" without claiming revocation, and the credentials survive it.

## 8. The three F2 review carries

All three were latent in F2 because `current_user` was wired into nothing. This
card wires it in, so all three are fixed here.

**a. `CLERK_AUTHORIZED_PARTIES` is mandatory.** F2 shipped it as "checked when
configured", which is a check that silently does nothing on the deployment that
most needs it. Unset now answers **503** at auth time, naming the variable. A
gate you can disable by forgetting an environment variable is not a gate.

Verified against the live instance: a **browser**-minted session token carries
`azp` = the page origin (`http://localhost:3113` in the live run). A token
minted through the Clerk *Backend* API carries none and is rejected — correct,
since it is not a browser session, but worth knowing before someone tries to
script against this API with one.

**b. `sid` is required.** Clerk mints two kinds of RS256 JWT from the same key
pair: short-lived session tokens, which carry `sid`, and instance JWT-template
tokens, which can be long-lived and minted for another purpose. Both verify
identically against the JWKS. Requiring `sid` is what stops a template token
authenticating here. Confirmed on real tokens: `sid`, `v: 2`, and `azp` are all
present on a live browser session token.

**c. Unknown `kid`s cannot drive outbound fetches.** `PyJWKClient.get_signing_key`
refreshes the JWK set on **every** `kid` miss, and the `kid` is attacker-chosen —
so a stream of junk tokens became a 1:1 stream of requests from our IP to Clerk.
`api/deps.py` now owns the key-set cache and refreshes at most once per
`UNKNOWN_KID_COOLDOWN_SECONDS` (30 s) no matter how many distinct unknown `kid`s
arrive. A test fires 50 random `kid`s and pins the fetch count at **+1**. Key
rotation still works: the first token under a new `kid` misses, the cooldown has
long since lapsed on an idle instance, and the refresh happens on that request.

**d. Ordering, and 503 vs 401.** Token verification is its own dependency
(`verified_claims`) declared **before** the session, so a missing or malformed
token 401s even on a deployment whose Postgres is down — previously it would
have 500'd, which is both the wrong status and a free liveness oracle on our
database. And a JWKS document we can *reach* but cannot parse is 503, not 401,
for the same reason an unreachable one is: a caller cannot fix our identity
provider serving garbage.

## 9. Frontend

Three files, no visual change to the dashboard.

- **`lib/api.ts`** — `/auth/login` and `/auth/logout` no longer send the admin
  secret (the backend refuses it, and offering it would be asking for an unowned
  link). `/auth/status` still sends it, so a flag-off operator build reports its
  own link. `/portfolio/*` still sends it when the build has one, but a build
  **without** one is only "locked" while sign-in is off; with the flag on, the
  Clerk token is the credential and a signed-out visitor gets the backend's 401.
- **`app/portfolio/page.tsx`** — the same condition, one line.
- **`components/portfolio/states.tsx`** — the locked/unauthorized gates say
  "sign-in is not switched on in this build yet · card L1" instead of "card F3
  lands per-user accounts", which is now false.

Pixel spot check (F2 methodology), operator configuration — stub source, admin
secret, `/portfolio`: **115 differing pixels of 2,239,200**, bounding box
`(448, 112)-(465, 123)`. A same-build self-diff is **115 pixels** in the
*identical* band, `(458, 112)-(473, 123)`. That box is the Refresh cooldown
countdown. Build output unchanged: `/` 133 kB, `/portfolio` 227 kB, same shared
chunk content hashes F2 recorded.

The one deliberate visual change is the locked-state copy above, which renders
only on a build with no credential at all.

## 11. What F4 / A1 consume

```python
from api.deps import CurrentUser                    # a verified Clerk user_id
from api.routes.portfolio import get_connector      # takes the user_id

@router.get("/whatever")
async def handler(user_id: CurrentUser):
    connector = get_connector(user_id)
    snapshot = await connector.fetch_snapshot(user_id)
```

Three rules for anything built on top:

0. **`/analyze` and the rest of the Lab endpoints are not per-user yet.** They
   still run on the *ambient* identity (`ind_money_auth.ambient_user_id()`) and
   are ungated. F3 stopped short of them deliberately — threading a `user_id`
   through the graph, the in-memory run registry and the paper watchlist is F4's
   whole job, and doing half of it here would have left two identity paths to
   keep in sync. Ledgered as REQUIRED in F4 and in the L1 ambient-removal
   checklist; there is a pointer comment on `analyze()`.
1. **Never call a connector without a `user_id` you verified this request.**
   The connector will refuse a mismatched one (`UserScopeError` → 403), but that
   is a backstop, not the design.
2. **`AuthStore.for_user(user_id)` is the only way to a token.** There is no
   ambient one outside single-tenant dev; `ambient_user_id()` exists solely for
   the legacy v1 research pipeline, resolves to the operator or `"local"`, and
   is never "whoever linked first".
3. **A missing link is `NotLinked` → 409, never an empty result.** An empty
   holdings table is a claim about what somebody owns.
