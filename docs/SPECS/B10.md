# B10 — Manual fixed deposits (backend)

Branch: `ishanavasthi/b10-fd-backend` (off `main` @ `98faa0d`). Issue #68.
Backlog: `BACKLOG.md` §"FD tracking" + §"Manual investments".

The user adds a fixed deposit by typing its **terms** — bank label, principal,
annual rate, compounding convention, start and maturity dates — and AlphaDesk
computes what it is worth, on every read, forever. Nothing is quoted, nothing is
fetched, and nothing derived is stored.

Two facts put this card ahead of every other manual asset class:

1. **The vendor is verified wrong about FDs.** B9/#65, with payloads, 2026-08-21:
   a ₹5,000 deposit reported at ₹162; `total_pnl` frozen at exactly −4,838 for
   five consecutive days; the FD bucket vanishing from `total_networth` on
   2026-08-18 and from the `assets` breakdown on 2026-08-20; `networth_holdings(FD)`
   returning `{"rows": []}` while the total still contained ₹10,162.
2. **An FD's value is computable, not quoted.** Principal + rate + compounding +
   two dates is the entire instrument. Every other manual class (gold, unlisted
   equity, property) needs a price somebody has to keep typing in.

**This card does not touch the vendor FD bucket.** Presenting or repairing what
IND Money reports is B9/#65. Everything here is *additive*: manual rows sit
alongside vendor rows and never rewrite, reconcile against or correct one.

## 1. Schema (migration `0008_manual_fds_table`)

```
manual_fds
  id             varchar(32)   PK      uuid4 hex, server-generated
  user_id        varchar(255)  FK users.id ON DELETE CASCADE, indexed
  label          varchar(120)
  principal      numeric(18,2)
  rate_pct       numeric(9,4)          annual percent (7.25 means 7.25%)
  compounding    varchar(16)           monthly|quarterly|half_yearly|yearly|simple
  start_date     date
  maturity_date  date
  created_at     timestamptz
  updated_at     timestamptz
```

- **Surrogate `id`.** Two deposits at the same bank may share a label, and the
  id has to survive an edit that changes every other field. `uuid4().hex`,
  generated server-side — a client-supplied id is a client-supplied FK.
- **`Numeric`, never float** (M1 rule 1). `principal` at (18,2) like every other
  money column; `rate_pct` at (9,4) because a bank quoting 7.1875% is ordinary.
- **`compounding` is a string, not a Postgres enum.** Adding a convention should
  be a code change, not a migration.
- **No Fernet.** FD terms are not credentials, and an encrypted column cannot be
  summed, filtered or ordered — which is the entire reason this lives in
  Postgres rather than a blob. Sensitivity-wise it sits exactly where the
  snapshot history beside it already sits.
- **No stored valuation column.** A saved `current_value` is wrong by the next
  morning, and a stale number that *looks* authoritative is the failure mode
  this whole card exists to fix.
- **`ON DELETE CASCADE`**, so L1's `DELETE /account` takes a user's deposits
  with them inside Postgres and needs **no code change at all**. The exhaustive
  zero-rows test in `test_account_deletion.py` proves it rather than assuming it.

Head moves `0007 → 0008`. `alembic check` is clean; `downgrade -1` drops the
index and the table.

## 2. Accrual math (`backend/services/manual_fd.py`)

Pure functions, **all `Decimal`** — not one `float()` call and not one float
literal in the module, enforced by an AST scan in the test suite.

### Year fraction — actual/365, clamped at both ends

```
t = max(0, (min(as_of, maturity_date) − start_date).days) / Decimal(365)
```

The lower clamp is a future-dated deposit: before it starts it has earned
nothing. The upper clamp is the **freeze at maturity** rule, and it lives in
this one expression so there is no second code path that could drift — past the
term everything downstream stops moving because `t` does.

### The two formulas

| convention | `n` | value |
|---|---|---|
| `monthly` | 12 | `principal × (1 + r/n)^(n·t)` |
| `quarterly` (default) | 4 | as above |
| `half_yearly` | 2 | as above |
| `yearly` | 1 | as above |
| `simple` | — | `principal × (1 + r·t)` |

where `r = rate_pct / 100`. `quarterly` is the default because Indian bank FDs
compound quarterly.

**The fractional exponent is a documented approximation.** A real bank credits
interest on period boundaries and pays simple interest on the stub after the
last one; `(1 + r/n) ** (n·t)` compounds continuously *within* the period
instead. The two agree **exactly** on period boundaries and differ by rupees,
not percent, in between — the honest trade for a formula a user can reconcile
against their own bank statement.

`Decimal ** Decimal` does the work at context precision (28 significant digits).
Money is quantized to paise (`ROUND_HALF_UP`) exactly once, at the end.

### Derived fields

- `accrued_interest = current_value − principal`
- `maturity_value` = the value at `maturity_date`. It is a property of the
  terms, so it is the **same number** whether asked before or after maturity.
- `matured = as_of >= maturity_date`
- `days_to_maturity = max(0, (maturity_date − as_of).days)` — floored at 0. A
  matured deposit has not "−1461 days" left; `matured` is the flag that says so.
  (The issue names the field but not its behaviour past maturity; this is the
  choice made, documented here.)

### "Today" is IST

`today_ist()` — the same `IST` constant `services.snapshots` owns, deliberately
**not** its `attributed_day()`. That helper attributes a run before 06:00 IST to
the previous day, which is a rule about when the capture job fires and has
nothing to do with what day a deposit has accrued to.

### `as_holdings(session, user_id, as_of) -> list[Holding]`

The bridge into M1's model:

| `Holding` field | value |
|---|---|
| `source` | `"manual"` |
| `external_id` | `fd.id` |
| `asset_type` | `AssetType.FD` |
| `name` | `fd.label` |
| `invested_amount` | `fd.principal` |
| `current_value` | the accrued value |
| `pnl`, `pnl_pct` | `models.derive_pnl(...)` — **never** inline arithmetic |
| `as_of` | the request's timestamp (aware UTC) |

`(source, external_id)` is M1's identity pair, so a manual row can never
collide with — or be mistaken for — anything IND Money returned, and the
frontend labels provenance off that one field. `Holding` is `extra="forbid"`
and refuses `invested_amount == 0`; the API's `principal > 0` guard is what
keeps that unreachable.

## 3. API — `/portfolio/fds` (`backend/api/routes/manual_fd.py`)

Its own router, registered in `api/main.py`, prefixed `/portfolio/fds` so it
sits on the portfolio surface and inherits its posture:

- **Identity:** `portfolio_identity` — a verified Clerk session token, or
  `"local"` under `ALPHADESK_SINGLE_TENANT=1`. **401** with neither, on all four
  methods.
- **Session:** `optional_session` (yields `None` with no `DATABASE_URL`).
- **Money as strings** via `_num`, dates as ISO-8601.
- **Another user's id is a 404, never a 403.** Every query is scoped on
  `user_id` in its own `WHERE` clause, so a row that is not the caller's is
  never loaded and existence is never leaked (the F4 §2 rule, applied to a new
  resource).
- The FK onto `users` is guaranteed by `ensure_user_row` before the insert —
  the same mechanism `api.main._persist_watchlist` uses, because `"local"` never
  goes through `register_identity`.

### Row shape

Every response body that contains a deposit contains exactly this:

```json
{
  "id": "3f6c1e0a9b2d4f7a8c5e1b0d9a7f6c3e",
  "label": "HDFC Bank FD",
  "principal": "100000.00",
  "rate_pct": "8.0000",
  "compounding": "quarterly",
  "start_date": "2025-01-01",
  "maturity_date": "2026-01-01",
  "current_value": "108243.22",
  "accrued_interest": "8243.22",
  "maturity_value": "108243.22",
  "matured": true,
  "days_to_maturity": 0,
  "created_at": "2026-08-21T09:14:02.117431+00:00",
  "updated_at": "2026-08-21T09:14:02.117431+00:00"
}
```

The five computed fields are **recomputed on every read** and stored nowhere.
That is the feature. The terms and the valuation ship in one object on purpose:
a client given only the terms would have to re-implement the accrual, and two
implementations of the same formula is how a screen ends up disagreeing with the
API about someone's money.

### `GET /portfolio/fds`

→ **200** `{"fds": [row, …], "note": null}`. Soonest maturity first, then
creation order.

No `DATABASE_URL` → **200** `{"fds": [], "note": "No database is configured, so
manual fixed deposits cannot be stored."}` — never a 500. This card sits on a
page whose live figures do not depend on Postgres and must not become the thing
that breaks it.

### `POST /portfolio/fds`

```json
{"label": "HDFC Bank FD", "principal": "100000", "rate_pct": "8",
 "compounding": "quarterly", "start_date": "2025-01-01",
 "maturity_date": "2026-01-01"}
```

→ **201** with the row. `compounding` is optional (defaults to `quarterly`);
every other field is required. Numbers may be JSON numbers or strings — both
land as `Decimal`.

### `PATCH /portfolio/fds/{id}`

Partial body, any subset of the six writable fields; omitted fields (and
explicit `null`s — no field here can be cleared) are unchanged. → **200** with
the updated row, `updated_at` bumped. An empty `{}` is a valid no-op.

### `DELETE /portfolio/fds/{id}`

→ **204**, empty body. A second delete is **404**, not a silent success.

### Errors

| status | when |
|---|---|
| **401** | no verified identity (single-tenant off, no token) |
| **404** | the id is not this caller's — including an id that never existed |
| **422** | `principal <= 0`, `rate_pct <= 0` or `> 50`, `start_date >= maturity_date`, unknown `compounding`, blank or >120-char `label`, a non-numeric or non-date value, or an unknown field (`extra="forbid"`) |
| **503** | `{"code": "no_database", "message": …}` on **any write** with no `DATABASE_URL` |

Schema violations are ordinary FastAPI/pydantic 422s. The one check the schema
cannot make — patching only `maturity_date` back before the *stored*
`start_date` — is a hand-raised 422 with `{"code": "invalid_terms"}`.

The `rate_pct <= 50` ceiling is a **typo guard** (7.25 entered as 725), not a
view about what rate a bank may offer.

### Why writes refuse instead of falling back to memory

This deliberately differs from the Lab watchlist, which keeps a per-user
in-memory dict when there is no database. A Lab run is a labelled simulation; a
fixed deposit is a financial record the user typed in. A success toast followed
by a silent loss on the next restart is a lie that stays invisible until the
data is already gone — so a deposit is durable data or it is an error.

## 4. Merging into the dashboard — additive, and after the cache

### `GET /portfolio/holdings?asset_type=FD`

Manual rows are appended **after** the `portfolio_cache` read *and* write. Two
consequences, both of them the point:

1. A deposit created a second ago shows up on the very next read, even though
   the vendor half is served from a 15-minute cache entry. **No invalidation
   dance** — `/portfolio/fds` never has to know a cache key exists.
2. Nothing manual is ever written into a cached vendor answer, so a manual row's
   accrual can never be frozen by a cache TTL.

Every vendor row is untouched. Every other asset type is byte-identical to
before this card. Manual rows carry `"source": "manual"`.

A failure in the merge degrades to "no manual rows" with a logged warning — it
must never take down a holdings page the source already answered.

### `GET /portfolio/summary`

Gains exactly one **additive** top-level block:

```json
"manual": {"total": "216486.44", "fd_count": 2}
```

`total` is the sum of accrued values, summed through the *same* valuation the
list and the holdings merge use, so the three can never disagree on one screen.
With no deposits (or no database) it is `{"total": "0", "fd_count": 0}` — the
same literal on both paths, so a client never has to tell `"0"` from `"0.00"`.

It is computed **per request on both paths** (cache hit and cache miss) and
cached nowhere. `net_worth`, `current_value`, `invested_total`, `pnl`,
`by_asset_type`, `by_asset_class`, `by_sector`, `by_market_cap`, `link_health` —
every vendor-derived field passes through **byte-identical**. This module's
never-recompute philosophy stands: adding a manual FD into the headline is a
**labelled** addition the frontend makes visible, not a silent adjustment made
here.

`movers`, `history`, `allocation`, the daily snapshots and `overview.py` are
**untouched**.

## 5. Scope

Owned here: `db/models.py` (`ManualFd`),
`alembic/versions/0008_manual_fds_table.py`, `services/manual_fd.py`,
`api/routes/manual_fd.py`, the two merge points in `api/routes/portfolio.py`,
the router registration in `api/main.py`, and
`tests/test_manual_fd.py` + `tests/test_api_manual_fd.py` (plus the three
one-line extensions to `conftest.py`, `test_api_portfolio.py`,
`test_db_identity.py` and `test_account_deletion.py` that keep the existing
exhaustive assertions exhaustive).

Not touched: `agents/`, `graph/`, `tools/`, `services/snapshots.py`,
`api/routes/{overview,account,internal}.py`, `api/deps.py`, the Lab. **No new
dependencies.**

Out of scope by the issue: the vendor FD bucket (**B9/#65**); manual FDs in
daily snapshots and the history trend line (a follow-up — `movers` already
classifies FD deltas as flows, so capture-time inclusion is safe later);
payout-type FDs (interest paid out periodically — only cumulative and simple
are supported); premature-withdrawal penalties; TDS; other manual asset classes
(#55's remainder); allocation-bar inclusion; AI-overview narration of manual
assets.

Testing: `docs/TESTING/B10.md`.
