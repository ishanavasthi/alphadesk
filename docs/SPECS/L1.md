# L1 — Pre-launch bar (THE INVITE GATE)

Branch: `feat/prelaunch` (off `main`, after U1). The last card: it ships the
legal + consent + deletion surface, enforces request-rate ceilings, executes the
F3 §5 interim-admin removal, and flips `NEXT_PUBLIC_AUTH_ENABLED` on. **Nothing is
invited before this merges and the operator finishes the wiring in
`docs/MORNING.md`.**

The moment someone else's net worth is in the database, AlphaDesk is a data
fiduciary under India's DPDP Act. Waitlist-gating does not exempt it. This card is
the surface that obligation requires.

---

## 1. Delete my data — `DELETE /account` (the acceptance centerpiece)

`backend/api/routes/account.py`. JWT-only (`CurrentUser`): a user deletes their
**own** data, and the id comes from a verified Clerk session — never a parameter,
never an admin path. The operation is single, ordered, and total:

1. **Revoke upstream first.** `logout(user_id)` (F3's `AuthStore.logout`) calls
   the broker's RFC 7009 revocation endpoint for the refresh token, *then*
   deletes the local `broker_links` row. Deleting our copy without revoking would
   leave a live grant on IND Money's side the user cannot see or reach. An
   upstream failure still proceeds (refusing would strand the user) and is
   reported in the response (`revoked_upstream`, `revocation_error`).

2. **Cascade-delete the user.** One statement — `DELETE FROM users WHERE id =
   :uid` — removes the row every other table hangs off. The cascade is a
   **schema guarantee**, not an ORM convention (V2_PLAN §6, `db.models`):

   | Table | Cascades via |
   | --- | --- |
   | `broker_links` | `user_id` FK `ON DELETE CASCADE` |
   | `oauth_pending` | `user_id` FK `ON DELETE CASCADE` |
   | `snapshot_days` | `user_id` FK `ON DELETE CASCADE` |
   | `snapshot_holdings` | `snapshot_id` → `snapshot_days` cascade |
   | `snapshot_raw` | `snapshot_id` → `snapshot_days` cascade |
   | `watchlist` | `user_id` FK `ON DELETE CASCADE` |

   No new migration and no tombstone: the cascades already exist. `alembic` is
   unaffected.

3. **Purge the process caches.** The DB cascade cannot reach memory. All of these
   are keyed by `user_id` and are cleared:
   - the Lab's `_RUNS` / `_ANALYSES` / `_ACTIONS` and the no-database
     `_PAPER_WATCHLIST` fallback (`api.main.purge_user_lab_state`);
   - the cached connector, which references the user's `AuthStore` and its
     decrypted tokens (`api.routes.portfolio.evict_connector`);
   - the seen-user write-avoidance set (`api.deps.forget_seen_user`) — **load
     bearing**: without it a re-used Clerk id signing in again would find no
     `users` row (`ensure_user` skips a "seen" id) and its first per-user write
     would fail an FK;
   - the adoption caches (`services.adoption.forget_user`).

**Frontend.** `components/clerk/DeleteMyDataDialog.tsx` — a type-to-confirm dialog
(the user types `DELETE` before the button arms) wired into the Clerk account
menu (`ClerkUserMenu`, per `docs/design/a4-shell.html`). On success it calls
`deleteAccount()` then `signOut({ redirectUrl: "/" })`. It lives under
`components/clerk/` because it imports `@clerk/nextjs` — the F2 containment
invariant that a vitest source scan enforces.

**Proof.** `backend/tests/test_account_deletion.py` seeds a user with a row in
**every** table plus in-memory Lab state, calls `DELETE /account`, and asserts
zero rows survive in each table and that revocation was called with the decrypted
refresh token. A second test pins the seen-user eviction (a re-signed-in id gets a
fresh `users` row). A row left behind anywhere is a failing test.

## 2. Consent at link time

`frontend/components/consent/LinkConsent.tsx`. A screen shown **before** the OAuth
redirect, naming exactly what the link will read (holdings, values, SIPs,
net-worth totals) and what it never does (no trading, no credentials — OAuth only;
no advice). Not a buried checkbox.

It is **unskippable in the link flow**: `useLinkConsent()` exposes
`begin(proceed)` (open the screen) and a `dialog` node; every Connect entry point
routes its OAuth start through it, and `proceed` runs only on agree —
synchronously inside the agree click, so a popup keeps its user activation. The
three entry points are the Lab top-bar button (`AuthProvider`), the `/portfolio`
gate (`app/portfolio/page.tsx`), and the landing gate (`ClerkLanding`). A source
scan (`tests/consent.test.tsx`) pins that each imports the hook, so a new Connect
button cannot quietly skip consent. The copy (`CONSENT_READS` / `CONSENT_NEVER`)
is single-sourced so the three cannot drift.

## 3. Privacy policy + terms

`frontend/app/(marketing)/privacy/page.tsx`, `terms/page.tsx`, framed by
`components/shell/LegalPage.tsx` (the U1 placeholder frame, now real content). The
privacy policy states plainly: what is read from the broker and why; where it is
stored (Neon/Postgres); retention (normalized snapshot rows kept; raw payloads
pruned at 90 days); that **no orders are ever placed**; that nothing here is
investment advice; and the DPDP deletion right. It **names the subprocessors**:

| Subprocessor | Function |
| --- | --- |
| **Groq** | the Lab's research prompts |
| **OpenAI** | portfolio narration — inputs not used for training by default, up to 30-day abuse-monitoring retention |
| **Clerk** | identity |
| **Neon** | database |
| **Hugging Face** | backend hosting |
| **Vercel** | frontend hosting |

The footer that links `/privacy` + `/terms` renders on **every** page — the
marketing group, `/demo`, `/portfolio`, and now `/lab` (a footer was added to the
Lab layout, which previously had none).

## 4. Spend cap + rate limits — the two ceilings, and why one 429s and one degrades

There are **two** independent controls, guarding different things:

- **The overview *spend* cap (A1, unchanged).** `agents.portfolio.spend` counts
  OpenAI *generations* per UTC day (global + per-user). Over the cap it
  **degrades** — the overview renders every computed number with the narrative
  panel showing "AI overview unavailable" — because A1 makes graceful degradation
  a hard requirement (a `spend_cap`→429 there would violate it). L1 verifies and
  tests this (`test_overview_api.py::test_overview_over_spend_cap_degrades`); it
  was shipped enforced, so nothing was rewired.

- **The request-*rate* cap (L1, new).** `backend/api/ratelimit.py` —
  `RateLimitMiddleware`, a fixed-window limiter with a **per-caller** ceiling
  (keyed by a hash of the bearer token, or client IP when anonymous) and a
  **global** ceiling, on the expensive surfaces `/analyze`,
  `/portfolio/overview`, `/auth/login`. Past either ceiling it answers **429**
  with `Retry-After`. This is the "cap returns 429 past the ceiling (global +
  per-user)" acceptance. Config (read per-request, so retunable without a
  restart), with defaults set high enough that ordinary use and the test suite
  never trip them:

  | Env | Default | Meaning |
  | --- | --- | --- |
  | `RATE_LIMIT_ENABLED` | `1` | off with `0`/`false` |
  | `RATE_LIMIT_WINDOW_SECONDS` | `60` | window length |
  | `RATE_LIMIT_PER_CALLER_MAX` | `60` | per token/IP per window |
  | `RATE_LIMIT_GLOBAL_MAX` | `600` | across all callers per window |

## 6. The flag flip

`frontend/.env.production` sets `NEXT_PUBLIC_AUTH_ENABLED=true`. Next loads it for
`next build` / `next start`, so the production build inlines the flag **on** — the
live site is behind Clerk Waitlist. Vercel dashboard variables override the file,
so a deploy can still be gated from the dashboard. The Clerk keys are secrets and
are **not** committed (set them on Vercel). The F2 landmine (flag-on needs *real*
keys, or `clerk-js` navigates every page to a `host_invalid` error) is why the
flip is last: the keys now exist. The flag-on production build was verified clean
(9 routes, middleware, `/sign-in` + `/waitlist` dynamic).
