# F2 — Clerk identity, flag-gated

Branch: `v2-foundation` (off `main` @ `7bc5e9c`, after S1).

**Nothing in this card is switched on.** It lands the whole identity layer —
backend token verification, frontend sign-in, Waitlist mode, a user menu, a
`users` row per person — with `NEXT_PUBLIC_AUTH_ENABLED` off, so `main` stays
deployable and the public site behaves exactly as it did before. Card L1 is the
deliberate release that flips the flag. F3 and F4 are the first code that
actually *uses* what is here.

No Clerk account existed while this was built. Everything below was verified
without one; §6 is the list of what real keys are still needed for.

---

## 1. The dependency contract F3/F4 consume

```python
from api.deps import CurrentUser        # Annotated[str, Depends(current_user)]

@router.get("/portfolio/summary")
async def summary(user_id: CurrentUser):
    ...
```

`current_user` reads `Authorization: Bearer <jwt>`, verifies it, ensures a
`users` row exists, and returns the Clerk `user_id` — a string like
`user_2fXaMpLe…`, which is exactly what `users.id` was declared to hold back in
F1. **No key migration is needed to adopt Clerk**, which is why that column was
a `str` and not a UUID.

**It is wired into nothing.** `api/main.py` does not import `api.deps`. Wiring
it into `/portfolio/*` today would lock the operator out of their own dashboard:
the live gate is still C0's admin secret, and no Clerk keys exist to replace it
with. F3 does the swap in one motion — Clerk token in, admin header out.

### What "verified" means

| # | Check | Failure |
|---|-------|---------|
| 1 | `Authorization: Bearer <token>`, non-empty (scheme case-insensitive) | 401 |
| 2 | header `kid` resolves against the cached JWKS | 401 |
| 3 | signature verifies under **RS256 only** | 401 |
| 4 | `exp` / `nbf` / `iat` within their windows | 401 |
| 5 | `iss` equals `CLERK_ISSUER` exactly | 401 |
| 6 | `azp` ∈ `CLERK_AUTHORIZED_PARTIES`, *when that is set* | 401 |
| 7 | `sub` present and non-blank | 401 |

Every 401 carries `WWW-Authenticate: Bearer`.

`algorithms=["RS256"]` at step 3 is what makes `alg: none` and the classic HS256
confusion attack (sign the token with the *public* key as an HMAC secret) fail
rather than pass — both have tests, because both are the kind of thing that
works by accident until it doesn't.

Step 6 is off by default because a deployment with no known frontend origin has
nothing to compare against. Clerk's own manual-verification guide is blunt that
leaving it off "can open your application to CSRF attacks", so set
`CLERK_AUTHORIZED_PARTIES` the moment there is a frontend origin.

### Networkless, after one fetch

`PyJWKClient` fetches the JWKS once and caches it for 300 s (`lifespan`), so
steady-state verification is a local RSA signature check with **no** round-trip
to Clerk. A test asserts one fetch across five verifications. Verification runs
on a worker thread (`asyncio.to_thread`) — the first fetch is network I/O and
the rest is CPU, and neither belongs on the event loop.

### Fail-closed, twice

- `CLERK_JWKS_URL` or `CLERK_ISSUER` unset → **503**, naming the missing
  variable. Never 200, and deliberately never 401: "this server was never
  configured" must not read as "your token is bad", or the operator goes hunting
  in the wrong place. Same convention as S1's `CRON_SECRET`.
- JWKS endpoint unreachable → **503**. Clerk being down is our outage; a 401
  would send a legitimately signed-in user off to re-authenticate against the
  very service we failed to reach.

### The `users` row

First time a `sub` verifies, `INSERT … ON CONFLICT (id) DO NOTHING` — not
SELECT-then-INSERT, because two requests from one brand-new user arriving
together would both find nothing and both insert.

Subsequent requests from the same `sub` skip the database entirely via a
process-local id set (`_SEEN_USERS`, capped at 10 000, dropped wholesale on
overflow). Two consequences to know:

- **`email` is captured at first sight only.** A default Clerk session token
  carries no email claim at all, so the usual outcome is NULL — a fine state for
  this column. An instance whose JWT template adds `email` gets it stored, and a
  later change in Clerk is *not* reflected until something syncs it (a Clerk
  webhook; a later card). The `user_id` is the identity, the email is a
  convenience for humans reading the table.
- **Deleting a `users` row out-of-band does not make the next request recreate
  it** inside the same process. Restart the app, or call `reset_seen_users()`.

### Why PyJWT and not `clerk-backend-api`

`clerk-backend-api` exists (currently 6.x) and does support networkless
verification. It also wants a `CLERK_SECRET_KEY` and an httpx `Request` object
to perform the same local RS256 check this does in ten lines against a JWKS URL
that is public by design. The backend holds no Clerk secret as a result — worth
having. `PyJWT==2.13.0` is pinned per repo policy; it was already installed as a
transitive dependency of `mcp`, and RS256 needs its `crypto` extra, which is the
`cryptography` already pinned for F1's Fernet columns.

## 2. Flag semantics

`NEXT_PUBLIC_AUTH_ENABLED` is read in exactly one place, `frontend/lib/auth.ts`,
and exported as `AUTH_ENABLED`. Only the literal string `"true"` enables it —
`"1"`, `"yes"` and `"TRUE"` are off, and a test pins that, because a flag that
half-matches is worse than one that never matches.

It is a **build-time** value. Next inlines every `NEXT_PUBLIC_*` into the
bundle, so flipping it means rebuild + redeploy, not a restart. That is the
intent: L1 is a release.

| | flag off (today, and shipped) | flag on |
|---|---|---|
| `<ClerkProvider>` | not mounted, chunk not downloaded | mounted inside `<body>` |
| `middleware.ts` | `NextResponse.next()` pass-through | `clerkMiddleware()` |
| `/sign-in`, `/waitlist` | **404** | Clerk's prebuilt forms |
| top-bar user menu | renders nothing, chunk not requested | avatar / "Sign in" |
| `Authorization` header | never attached | attached when a session exists |
| C0 admin header | attached as before | attached as before (F3 removes it) |

### Flag off must mean "downloads no Clerk"

Not "downloads Clerk and declines to run it". Whether a minifier would
eliminate a statically-imported-but-unreachable `@clerk/nextjs` is a question
about that release of webpack, so the gates are placed where the answer is
structural instead:

- **`components/Identity.tsx` is a server component** (no `"use client"`). A
  client chunk that a server component never renders is never sent to the
  browser. This is the provider gate, rendered from `app/layout.tsx`.
- **`components/UserMenu.tsx` cannot use that trick** — it sits under
  `TerminalChrome`, which is a client component (`usePathname`), so everything
  below it is client code. It gates a `next/dynamic` import instead: an async
  import is a separate chunk by construction, and with the flag off `dynamic()`
  is never called, so the chunk is never requested.
- **`/sign-in` and `/waitlist` are server components that call `notFound()`**
  when the flag is off, so both still 404 exactly as they did before this card,
  and their Clerk chunks are never served.
- `@clerk/nextjs` is imported **only** from `components/clerk/` and
  `middleware.ts`. A vitest source scan enforces it, with a positive control so
  a broken detector cannot report "all clear" forever.

Measured, flag off, against a build of the pre-branch tree:

| | result |
|---|---|
| `/portfolio` screenshot | **0** differing pixels of 1 296 000 |
| `/` screenshot | 230 differing pixels — inside the *same* bounding box that two screenshots of one unchanged build differ by (242). The page pulses; that is all this is. |
| First Load JS `/` | 132 kB → 133 kB |
| First Load JS `/portfolio` | 227 kB → 227 kB |
| shared chunks | same content hashes as pre-branch (`255-69a4a78f…`, `4bd1b696-409494ca…`) |
| any Clerk chunk requested | none, on either page |

### The one honest delta

`frontend/middleware.ts` now exists, and Next invokes it on matching requests
where before this card there was no middleware at all. **That is not a choice.**
`config.matcher` has to be a static literal — Next parses it out of the file
rather than evaluating it, and `matcher: FLAG ? [...] : []` fails the build with
*"Unsupported node type ConditionalExpression at config.matcher"*. So the
matcher is unconditional and the *body* carries the flag: with the flag off the
handler is a bare `NextResponse.next()` and `clerkMiddleware()` is never
constructed (constructing it without a publishable key throws).

The cost is one pass-through invocation per request and ~55 kB of dead code in
the middleware bundle — server-side only, nothing in the client bundle, and no
change to what any request returns.

## 3. Waitlist mode

AlphaDesk opens as a waitlist: joining is a *request*, not a signup. `/waitlist`
renders Clerk's `<Waitlist />`; a submission gets a confirmation email, and a
second email with sign-in instructions once an operator approves the person in
the Clerk Dashboard. **Approval is a human act — nothing in this repo grants
it.**

Waitlist mode itself is a **Dashboard setting** (Configure → Restrictions →
Sign-up mode → Waitlist), not a prop. Rendering `<Waitlist />` against an
instance that is not in Waitlist mode gets an error from Clerk rather than a
form.

`<ClerkProvider waitlistUrl="/waitlist">` is what makes the sign-in card's
"no account?" link point at the waitlist instead of a sign-up form nobody is
allowed to complete.

Both routes are optional catch-alls (`[[...sign-in]]`, `[[...waitlist]]`)
because Clerk routes its own multi-step flows — second factor, password reset,
SSO callback — as sub-paths. A plain `page.tsx` would 404 halfway through a
sign-in.

## 4. The `useAuth` → `useIndMoney` rename

`components/AuthProvider.tsx` exported a hook called `useAuth`. So does Clerk.
Two hooks of the same name, imported from different modules, answering different
questions — *is a broker linked* versus *who is looking at this* — is a gate on
the wrong condition waiting to happen, and it compiles and renders either way.

`useIndMoney` is also the accurate name: that hook has never known anything
about who the visitor is. After F3 the two facts become genuinely independent
(a signed-in user who has not linked IND Money).

Call sites updated: `app/page.tsx`, `components/AuthButton.tsx`,
`components/ResultsDashboard.tsx`. The provider component and file keep their
names; `components/Identity.tsx` is the Clerk one, and the two are labelled in
`app/layout.tsx` so the distinction survives the next reader. A vitest source
scan asserts zero surviving `useAuth` imports from `AuthProvider`.

## 5. Token attachment

`lib/api.ts` has one wrapper, `apiFetch`, and **every** backend call goes
through it — a test pins that no bare `fetch(\`${API_BASE}…\`)` survives, because
the failure mode of the alternative is one forgotten call site that works
perfectly today and 401s the day F3 turns the gate on.

`withAuth()` returns the caller's headers *unchanged* when the flag is off or
nobody is signed in, so a request from this build is indistinguishable from one
before F2. The interim C0 `x-alphadesk-admin-secret` header is untouched and
rides alongside — **F3 is what removes it**, once a verified `user_id` can take
over the job.

Tokens are fetched per request rather than cached: Clerk session tokens live
about a minute and Clerk refreshes them in the background, so a cached one is a
stale one. `ClerkIdentityProvider` registers Clerk's `getToken` with
`lib/auth.ts` on mount and clears it on unmount. A getter that throws yields
`null`, not an exception — Clerk Core 3's `getToken` throws
`clerk_runtime_not_browser` outside the browser, and an unauthenticated request
is recoverable where an exception in every `fetch` is not.

## 6. What still needs real keys

Everything below is unverifiable until the operator creates a Clerk instance.
Nothing below blocks this card; all of it blocks L1.

| Needs real keys | Why |
|---|---|
| Any Clerk UI rendering at all | `<SignIn />`, `<Waitlist />` and `<UserButton />` are shells; their markup comes from `clerk-js`, loaded from the instance's Frontend API. With a placeholder key that host answers `400 host_invalid`. |
| A usable site with the flag **on** | Worse than "the widgets don't appear": a `pk_test_` key makes `clerk-js` run its dev-browser handshake, which **navigates the browser to the Clerk Frontend API**. With a fake host every page lands on Clerk's error JSON. The server still renders correctly (200, correct HTML) — the takeover is client-side. Flag on ⇒ real keys, no exceptions. |
| Waitlist mode behaviour | It is a Dashboard setting; there is no Dashboard yet. |
| `CLERK_JWKS_URL` / `CLERK_ISSUER` correctness | Both derive from the instance's Frontend API URL, which does not exist yet. |
| End-to-end backend verification | The suite mints its own RSA keypair and serves its own JWKS, so every code path *except* "did Clerk really issue this" is covered. See `docs/TESTING/F2.md` §4 for the one-command check to run once keys exist. |

### Operator wiring, when the time comes

Clerk Dashboard → Configure → API keys, then:

| Where | Variable | Value |
|---|---|---|
| Vercel | `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` | `pk_live_…` (public by design) |
| Vercel | `CLERK_SECRET_KEY` | `sk_live_…` — **not** `NEXT_PUBLIC_` |
| Vercel | `NEXT_PUBLIC_AUTH_ENABLED` | `true` **only at L1** |
| HF Space | `CLERK_JWKS_URL` | `https://<frontend-api>/.well-known/jwks.json` |
| HF Space | `CLERK_ISSUER` | `https://<frontend-api>` |
| HF Space | `CLERK_AUTHORIZED_PARTIES` | the live frontend origin(s) |

**Mind the `.json`.** A production custom domain serves the JWKS *only* at
`/.well-known/jwks.json`, while a `*.clerk.accounts.dev` development domain also
answers `/.well-known/jwks` — so a URL that works in dev can 404 in production.

## 7. Clerk-docs drift found while building

The brief flagged four things as "Likely, not verified". Checked against current
Clerk docs:

| Claim | Verdict |
|---|---|
| `clerk-backend-api` is the PyPI package name | **Confirmed** (currently 6.x). Not used — see §1. |
| Networkless RS256/JWKS verification is supported | **Confirmed**, and it is Clerk's own documented "manual JWT verification" path. |
| `<Waitlist />` component and Waitlist mode exist | **Confirmed** (`@clerk/nextjs` ≥ 6.2.0; Waitlist mode is a Dashboard setting). |
| `<ClerkProvider>` wraps the app | **Drifted.** Clerk Core 3 (`@clerk/nextjs` v7) requires it **inside `<body>`**, not wrapping `<html>`. |

Other drift worth recording, none of it in the brief:

- **`<SignedIn>` / `<SignedOut>` / `<Protect>` are removed in Core 3**, replaced
  by `<Show>`. This card uses neither — `ClerkUserMenu` branches on
  `useUser().isLoaded` so it can reserve the avatar's space and not reflow the
  top bar on hydration — but any code copied from an older Clerk tutorial will
  reference the removed components.
- **`useAuth().getToken` no longer returns `undefined` during SSR**; it is a
  function that *throws* `clerk_runtime_not_browser`. `lib/auth.ts` catches it.
- **`clerkMiddleware()` does not protect routes by default**, and Clerk's own
  guidance is that middleware is the wrong place to protect them — protect at
  the resource. F3/F4 should follow that: `current_user` on the endpoint, not a
  matcher in `middleware.ts`.
- **Next 16 renames `middleware.ts` to `proxy.ts`.** This app is on Next 15;
  renaming belongs to a future Next 16 upgrade.
- **`config.matcher` must be a static literal** — see §2's "one honest delta".
- **`@clerk/nextjs`'s React peer range is `^18 || ~19.0.3 || ~19.1.4 ||
  ~19.2.3`**, which the repo's exact `19.0.0` did not satisfy; an unmet peer is
  an `ERESOLVE` failure on a clean Vercel install, so `react`/`react-dom` moved
  to `19.0.8` — the smallest bump that satisfies it. Clerk v6 has the identical
  peer range, so staying on v6 would not have avoided it.
