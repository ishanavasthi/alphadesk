# M1 — Normalized portfolio model + connectors

Branch: `feat/portfolio-model` (off `main` @ `8ae48b7`, after the C2 human gate).
Scope: **additive.** `git diff main --name-only` touches only `backend/portfolio/`,
`backend/tests/` and `docs/`. No API route, agent, graph node, tool, migration or
requirement changed.

What lands here is the vocabulary the rest of v2 speaks about money: a
source-neutral `Holding` (and its aggregates), one connector interface, and two
real implementations of it. Everything asserted below traces to
[`docs/ind_money_payloads.md`](../ind_money_payloads.md) — the C2 spike is the
authority, and where it and an earlier plan assumption disagreed, C2 won.

## 1. The model (`backend/portfolio/models.py`)

### `Holding`

| Field | Type | Notes |
| --- | --- | --- |
| `source` | `str` | `"ind_money"` \| `"stub"`. Half of the identity pair. |
| `external_id` | `str` | Stable id **within** a source. See §2. |
| `asset_type` | `AssetType` | 16 real values + `UNKNOWN`. |
| `asset_type_raw` | `str \| None` | The source's own string, verbatim. |
| `symbol` | `str \| None` | `None` from IND Money — it publishes no ticker on a holdings row. |
| `name` | `str \| None` | Display label. Empty strings normalize to `None` (the vendor returned one in 1 of 14 real rows). |
| `isin` | `str \| None` | `None` from IND Money — no ISIN-labelled field exists. |
| `units` | `Decimal \| None` | |
| `avg_cost` | `Decimal \| None` | **Derived**, not sourced: `invested_amount / units`, 4 dp, only when both are known and units ≠ 0. |
| `invested_amount` | `Decimal \| None` | `None` means **unknown cost basis**. |
| `current_price` | `Decimal \| None` | |
| `current_value` | `Decimal` | The only always-required number. |
| `pnl` / `pnl_pct` | `Decimal \| None` | Derived, nullable. Never present when `invested_amount` is `None`. |
| `currency` | `"INR"` | See §4. |
| `as_of` | `datetime` (tz-aware, UTC) | **Stamped by the connector.** No payload carries a date. |
| `raw` | `dict` | The source row, for forensics. |

`name` is the one field beyond the plan's list. It exists because the vendor's
display label maps nowhere else and dropping it would force every caller to
reach into `raw` — which is exactly the boundary violation §6 forbids.

**There is no `xirr` anywhere in the module, by design.** C2 Q1: the vendor's own
field was `0` in 14 of 14 rows, no payload carries a dated cashflow, and no tool
in the 15-tool inventory supplies one. The return metric is `pnl_pct` (simple
cumulative return) and it must never be labelled XIRR.

### Aggregates

- **`AllocationSlice`** — one bucket: `label`, optional `asset_type` /
  `asset_type_raw`, `invested_amount`, `current_value`, `pnl`, `pnl_pct`,
  `weight_pct`. The same "no P&L without a cost basis" rule applies.
- **`Allocation`** — the result of one `(asset_type, by)` request.
- **`PortfolioSnapshot`** — `net_worth` (net of liabilities), `gross_value`,
  `invested_total`, `liabilities_total`, plus four `AllocationSlice` lists
  (`by_asset_type`, `by_asset_class`, `by_sector`, `by_market_cap`).
- **`Sip`** — ⚠️ **UNVERIFIED row shape**, see §7.

`sum_holdings_value(holdings)` exists and is deliberately *not* a method on
`PortfolioSnapshot`: the two numbers do not agree, and putting them on the same
object invites someone to assert that they do (§5).

### `AssetType`

The 16 values from the server's own input schema — `IND_STOCK, MF, US_STOCK,
BOND, EPF, NPS, SA, FD, CRYPTO, INSURANCE, VEHICLE, RE, RD, AIF, PMS, PPF` —
plus `UNKNOWN`, which is **ours, not the vendor's**, and is never sent as a
query argument (`AssetType.queryable()` returns exactly the 16).

`AssetType.coerce()` never raises. Any unrecognized string becomes `UNKNOWN`
with the original preserved in `asset_type_raw`. This is not defensive
programming for its own sake: `networth_snapshot` really does report a
`US_STOCK_WALLET` bucket that `networth_holdings` refuses to accept, and it is
~2.3% of the operator's portfolio. It must reach the totals, tagged, not be
dropped and not crash the parse.

`BreakdownBy` = `assets | sector | market_cap`.

## 2. Identity — how `external_id` is derived, and why it is stable

Identity is `(source, external_id)`. Per source:

**IND Money:** `"<asset_type_raw>:<investment_code>"`.

- `investment_code` is the vendor's own instrument id and was present and
  non-empty on all 14 observed rows.
- It is **prefixed with the asset type** because nothing guarantees the code
  space is shared across asset types; a fund code and a deposit code colliding
  would silently merge two positions. The prefix costs nothing and removes the
  question.
- **`broker` is deliberately not part of the id.** C2 Q2: it was an empty string
  in 4 of 14 rows (every FD and every SA row), so keying on it would collapse
  those into one bucket — and a holding that moves broker is still the same
  holding.
- **Fallback** when the code is missing or empty:
  `"<asset_type_raw>:h:<sha1-16 of investment, broker, assetclass_l2,
  market_cap>"`, JSON-encoded before hashing so `("a|b",)` cannot collide with
  `("a","b")`. This is **weaker**: it is stable only while those four fields are.
  A renamed fund gets a new id. That is accepted — the alternative (row index)
  is not stable across a single re-fetch, which is worse.

**Stub:** the fixture's own `external_id` (`DEMO-MF-0001`, …), which is a fixed
identifier in an invented dataset.

## 3. Degrade rules (each one is a C2 finding)

1. **`Decimal` for every money/percent value, coerced through `str`.** The API
   emits `int` for an integral value and `float` otherwise — for the same field,
   across rows. `Decimal(0.1)` is not `0.1`; `Decimal(str(0.1))` is.
2. **`invested_amount == 0` (or absent, or `null`) means UNKNOWN cost basis**,
   not "invested nothing" — the vendor documents this for linked brokers. All
   three encodings map to `None`, and `Holding` **refuses to be constructed**
   with `invested_amount == 0` at all, so no connector can quietly opt out.
3. **No P&L without a cost basis.** When `invested_amount` is `None`, `pnl` and
   `pnl_pct` are `None` — the model rejects any other combination. Note the
   asymmetry that matters: the source's *own* `pnl_per` of `0` on a cash-like
   row is a real answer ("no return by nature") and is passed through; a `0`
   or `-100%` **computed** from an unknown basis is fabricated and cannot exist.
4. **Value is never derived as units × price.** 4 of 14 real rows (all SA, all
   FD) carry `total_units` and `unit_price` of exactly `0` beside a non-zero
   value — the decomposition is undefined, not zero. Such rows map to
   `units = None`, `current_price = None`. A row whose *value* is also `0` is a
   genuine zero and keeps its zeros (and its real −100% P&L).
5. **Empty asset types return `[]`**, not an error. 11 of 16 were empty.

## 4. Currency stance (decided at the D-gate — verbatim)

> No payload carries any currency field, and the vendor reports all values
> INR-converted (it sums `US_STOCK` into `total_networth` itself). So the
> connector sets `currency="INR"` for all rows, and the US-exposure signal is
> `asset_type ∈ {US_STOCK, UNKNOWN(US_STOCK_WALLET)}` — downstream display can
> badge them. If a currency field ever **appears** in a payload with a non-INR
> value, the connector **raises**.

As implemented:

- `Holding.currency`, `AllocationSlice.currency`, `Allocation.currency`,
  `PortfolioSnapshot.currency` and `Sip.currency` all default to `"INR"` and
  **reject any other value** at the model level.
- Every successful IND Money payload is walked for a key containing
  `currency` before it is parsed. A value that is not `INR` raises
  `NonInrValue`, naming the JSON path. An `INR` value passes (the assumption is
  simply confirmed).
- `is_us_exposure(asset_type, asset_type_raw)` is the display signal;
  `PortfolioSnapshot.us_exposure_slices()` surfaces the buckets D1 must badge or
  exclude from a headline INR figure.

This is an assumption the source gives us **no field to verify**. It is written
as an assertion rather than a comment so that the day it breaks, it breaks
loudly instead of silently corrupting every cross-asset total.

Consistent with the operator's 2026-08-15 S1 addition (a daily USD/INR rate
captured into `snapshot_days.usd_inr_rate`): that rate is for **conversion
display math, never re-summing** — holdings stay vendor-INR, which is exactly
what this model encodes. M1 stores no FX rate and performs no conversion.

## 5. Reconciliation: none, ever

`sum(holdings) != snapshot total`, by construction:

- the un-enumerable `US_STOCK_WALLET` bucket is ~2.3% of the total and no call
  can list its line items;
- adding it back does **not** fix it — per-type sums miss their own buckets by
  up to 0.944%, because the snapshot and the holdings rows are priced from
  different refreshes.

So: `PortfolioSnapshot` carries the vendor's own `total_networth` /
`total_current_value` / `total_invested` **passed straight through**, never
recomputed. Nothing in M1 asserts equality, and the contract test asserts the
*opposite* — that the two differ on both connectors — so a future card cannot
add such a check without a test going red first.

## 6. The connector interface (`backend/portfolio/connectors/base.py`)

```python
async fetch_snapshot(user_id) -> PortfolioSnapshot
async fetch_holdings(user_id, asset_type) -> list[Holding]
async fetch_allocation(user_id, asset_type, by) -> Allocation
async fetch_sips(user_id) -> list[Sip]
async link_health(user_id) -> LinkHealth
```

**`user_id` is explicit on every method, from the first line each was written.**
It is the constant `"local"` at call sites until F3 — never implicit, never a
module global. Retrofitting a user argument into a shipped data path is how
cross-user leaks get written.

### `link_health` states

| State | Meaning |
| --- | --- |
| `linked` | A usable credential exists now. |
| `expiring` | Usable, but inside the expiry threshold (default 300s) and not yet renewed. |
| `needs_relink` | No usable credential; the user must authorize again. |
| `revoked` | The source **explicitly rejected** our credential. Strictly stronger than `needs_relink`. |

The interface deliberately does **not** assume the source can refresh — a future
connector may be authorization-code-only, in which case "we hold a refresh
token" is no evidence of health at all. The IND Money implementation therefore
derives its answer from `tools/ind_money_auth.auth_status()`, which actually
verifies the token (refreshing when it can) rather than trusting its presence,
and treats a definitive rejection (`MCPAuthInvalid`) as `revoked` — sticky for
the process, since a dead grant does not come back on its own. A transient
failure (`MCPAuthError`) reports `needs_relink`, not `revoked`. The status
provider is injectable, which is the seam F3 replaces with a per-user link row.

### `IndMoneyConnector`

- Transport is the `_call_mcp_tool` + `_unwrap` pattern from
  `tools/ind_money.py`, **injected** rather than imported at module scope, so
  the tests drive the exact same code path off the C2 fixtures without a
  network, and F3 can hand it a per-user credential.
- **One process holds one credential set**, so the connector is bound to a
  single `user_id` and raises `UserScopeError` for any other — before any
  network call. Until F3 that guard is what stops a multi-user deployment from
  serving the operator's portfolio to every visitor.
- `fetch_holdings(user_id, AssetType.UNKNOWN)` raises `UnsupportedAssetType`:
  the source cannot enumerate a bucket outside its own enum. Read those off
  `fetch_snapshot().by_asset_type` instead.

### `StubConnector`

A **second real implementation**, not scaffolding. It backs U1's public `/demo`
route and makes F4's cross-user isolation testable in CI forever (its
`portfolios` map gives two users two genuinely different portfolios). Its data
lives in `backend/tests/fixtures/demo/` and is **entirely invented** — see that
directory's README for the edge cases it deliberately carries. The fixtures are
written in the *model's* vocabulary, not a vendor's; a stub that parsed a vendor
shape would be a second IND Money connector in disguise and would never exercise
the seam.

### Rate-limit policy

C2 §2.5: a throttled call is **`isError: false`** with an `error` body that
**replaces** the payload, so `payload["holdings"]` raises `KeyError` instead of
retrying. Implemented as:

1. Every call checks for an `error` key **before** touching `data` / `holdings`.
2. `error == "rate_limit_exceeded"` → bounded retries (default 2), each paced by
   the server's own `retry_after_seconds`, **capped** (default 60s) so a hostile
   or absurd delay cannot hang a request. Exhausted → `RateLimited`, carrying
   `scope`, `window`, `limit`, `current`, `cost`, `retry_after_seconds` and the
   whole body.
3. Nothing is hard-coded about either tier. The per-tool tier (15/min) trips
   first on single-tool bursts; the global tier is 30/min; `networth_allocation_
   breakdown` costs 2. A client that hard-codes one tier misreads the other as a
   server-wide outage.
4. **The 48-call allocation grid is never swept.** `fetch_allocation` is
   singular by construction — one request, one `(asset_type, by)` slice, fetched
   lazily when a caller actually wants it. A full sweep would cost 96 units
   against a 15/min budget and trip after 7 calls.
5. Any other `error` code → `SourceReportedError`. Any missing/mistyped payload
   key → `PayloadShapeError` (typed, with a message that names the rate-limit
   possibility), never a bare `KeyError`.

## 7. Explicitly-unverified boundaries

### `IND_STOCK` holdings rows — UNVERIFIED

The one asset type AlphaDesk exists for returned **zero rows** on the only
account ever captured, inside a **19-key live-trading envelope** that shares no
key with the aggregator shape beyond `holdings`. **No populated `IND_STOCK` row
has ever been observed.** The snapshot confirms the account simply holds no
Indian stocks (it carries no `IND_STOCK` bucket at all), so this is an empty
slice rather than a broken endpoint — but the row shape is still unknown.

Mapped per the documented aggregator shape, and **strictly**: for `IND_STOCK`
only, any unexpected key or a missing value raises `UnverifiedShapeError`
(a `PayloadShapeError` subclass) naming the offending keys. Every other asset
type stays *tolerant* of a new key — a verified shape gaining a field is a
vendor addition, not a broken assumption. The asymmetry is the point.

**This boundary is closed only by a capture from an account that actually holds
Indian stocks.** Until then, D1 rendering an `IND_STOCK` holdings table is
rendering a guess.

### SIP rows — UNVERIFIED

Both SIP endpoints returned zero rows, so no populated row has ever been seen.
Mapped defensively by alias (`sip_amount`/`amount`, `fund_name`/`stock_name`/…),
with anything unmapped left in `raw` and an unparseable date left `None` rather
than guessed at. `next_execution_at` is **forward-looking** — the vendor's own
description promises only the next execution and the current month's
installments, which is why no money-weighted return is derivable even if these
were populated.

### Liability rows

`liabilities.loans` and `liabilities.credit_cards` were empty arrays in the
capture, so their element shape is unverified. M1 reads only
`liabilities.total`, which is a scalar and was populated.

## 8. The boundary rule

**No vendor field name appears above `backend/portfolio/connectors/.`** This is
enforced by `backend/tests/test_portfolio_boundary.py`, which greps
`backend/portfolio/` (excluding `connectors/`) for the vendor's field names
(`pnl_per`, `holding_percent`, `market_value`, `investment_code`,
`assetclass_l2`, `total_networth`, `invested_value`, `unit_price`, `total_units`,
`total_pnl`, `progress_value_percentage`, `return_percentage`, `xirr`, the
live-trading flags) **and its tool names**, plus a non-vacuity check that those
same names *do* appear below the boundary.

`invested_amount`, `current_value`, `asset_type` and `market_cap` are excluded
from the ban: they are the model's own names too, and banning them would be
banning our vocabulary. (`sum_holdings_value` is named as it is precisely
because `total_current_value` is a vendor field name.)

## 9. What M1 deliberately does not do

- **No database tables.** The model is in-memory value types; persisting them is
  S1's card, after D1 shows which fields are actually rendered.
- **No API route.** Nothing in `api/main.py` imports `portfolio.*` yet.
- **No aggregation across asset types.** C2 Q4 says a naive cross-asset sum is
  unverifiable; the snapshot's own totals are passed through instead, and the
  US-exposure signal is exposed so D1 can exclude or label them.
- **No new dependency.** Nothing was added to `requirements.txt`.
