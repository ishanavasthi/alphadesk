# C2 — IND Money data spike (HUMAN GATE at the end)

Branch: `spike/ind-money-portfolio` (off `main` @ `8caee5d`).
Scope: **investigation + documentation + fixtures only. Zero application code
changed.** `git diff main -- backend/api backend/agents backend/graph
backend/tools backend/db frontend` is empty.

The findings themselves live in
[`docs/ind_money_payloads.md`](../ind_money_payloads.md) — that is the document
the human gate is about. This file records *what was done*, so the work is
reproducible and auditable.

## Why this card existed

Nobody had ever seen a `networth_*` response. Three downstream cards (M1 model,
D1 dashboard, A1 AI overview) were resting on payload shapes that were pure
guesswork. This card replaced the guesses with evidence and stopped M1 from
modelling fiction.

## What was probed

Against the operator's linked account, over the live `indmcp` MCP server
(v1.26.0, protocol `2025-11-25`), using the repo's own auth path
(`tools/ind_money_auth.get_access_token` → hourly access token auto-refreshed
from the stored refresh token in `backend/.ind_money_token.json`) and the repo's
own unwrapping helpers (`tools/ind_money._unwrap`, `._extract_text`).

| Probe | Calls | Result |
| --- | --- | --- |
| `list_tools` | 1 | **15 tools** + full input schemas captured |
| `networth_snapshot()` | 1 | populated |
| `networth_holdings(asset_type=…)` | **16** — every value of the server's actual enum | 4 asset types returned rows (14 rows total); 12 returned none |
| `networth_allocation_breakdown(asset_type=…, breakdown_by=…)` | **48** — full 16 × 3 cross-product | 8 combinations returned rows; 40 empty |
| `mf_sips()`, `indian_stocks_sips()` | 2 | both returned **zero rows** |
| DCR probe (`/register`, second registration, fresh client name) | 2 registrations + 1 discovery | both **201**; independent credentials; `portfolio:read` scope; no rate-limit headers. ⚠️ **Raw capture lost and deliberately not re-run** — see below |
| Unauthenticated `list_tools` (control) | 1 | fails — confirms tool calls need auth while `/register` does not |

Total: **72 tool/HTTP calls** (1 + 1 + 16 + 48 + 2 + 3 + 1) producing **67
payload capture files** (snapshot + 16 holdings + 48 breakdowns + 2 SIP), plus
the tool inventory and the probe records.

The DCR probe did **not** log out, revoke, or invalidate the existing client or
token — it only added new registrations.

**The DCR probe capture was not restored.** Every other capture in the set is a
read; `/register` is not — each probe call mints a **real OAuth client on the
vendor's server**, which then persists with no known cleanup path. Re-running a
side-effecting probe purely to re-create a lost file is not a trade worth
making, so Q5's probe bullets are reproduced from the run-1 notes and are
flagged in the payload doc as not re-verifiable. Q5's conclusion does not rest
on them: it rests on `tools/ind_money_auth.begin_login()`, which registers a
fresh client on **every** login and carries it through `/authorize` + `/token`
in production — checkable in this repo, with no probe at all.

### Drift against the plan's guesses

None on names or enums. `networth_snapshot`, `networth_holdings`,
`networth_allocation_breakdown`, `mf_sips` and `indian_stocks_sips` all exist
with exactly the guessed names; the `asset_type` enum matched the plan's
expected 16-value universe exactly, and `breakdown_by` matched
`assets`/`sector`/`market_cap`.

The drift was all in the **responses**, and it was substantial — see
`ind_money_payloads.md` §2. The three that matter most:

1. `networth_holdings` returns **two structurally different payloads** depending
   on asset type (a 14-key aggregator row vs a 19-key live-trading envelope for
   `IND_STOCK`).
2. `networth_snapshot` reports an `asset_type` bucket (`US_STOCK_WALLET`) that
   the holdings tool's enum **does not accept**, so it can never be enumerated.
3. There is **no date field and no currency field anywhere** in any payload.

## Go/no-go — verbatim

> **Verdict: GO for M1 — with scope changes to all five downstream cards and one
> blocking unknown that M1 must design around rather than assume away. The kill
> criterion is NOT triggered.**
>
> The kill criterion in the plan was: *if `networth_snapshot`/`networth_holdings`
> return no usable per-holding values, D1/S1/A1 as specified are dead.* They do
> return usable per-holding values — a stable 14-key row with invested amount,
> market value, units, unit price, absolute and percentage P&L, and portfolio
> weight, populated in 14 of 14 observed rows, plus a clean 2-decimal net-worth
> total. D1, S1 and A1 survive.
>
> **Scope changes, by card:**
>
> - **A1 (AI overview) — CHANGED. Its XIRR metric is dead.** `xirr` was `0` in
>   14 of 14 rows, there are no dated cashflows in any payload, and no tool in the
>   inventory supplies them. Replace with `return_percentage` from
>   `networth_snapshot` (simple cumulative return), and do not call it XIRR.
> - **D1 (dashboard) — CHANGED, twice.** (a) Drop the holdings-table XIRR column
>   or relabel it `Return %` sourced from per-row `pnl_per`. (b) Headline totals
>   must not silently blend `US_STOCK`/`US_STOCK_WALLET` into an INR figure —
>   exclude them or label the assumption (Q4).
> - **M1 (model) — CHANGED, three ways.** (a) One holdings model does **not**
>   fit: `IND_STOCK` returns a structurally different 19-key live-trading
>   envelope, not the 14-key aggregator row. (b) All money/percent fields must be
>   `float`/`Decimal`, never `int` — the API emits both for the same field.
>   (c) `invested_amount == 0` means *unknown cost basis* (vendor-documented for
>   linked brokers) and must be nullable in the model, never fed into a P&L
>   calculation.
> - **S1 (snapshots) — CHANGED, mildly.** There is **no `as_of` field in any
>   payload**. S1's calendar-day attribution must stamp its own capture time at
>   ingest; the vendor gives it nothing to anchor to. Also: do not add a
>   reconciliation constraint between stored holdings and stored net worth — the
>   unenumerable `US_STOCK_WALLET` bucket makes it ~2.3% off by construction, and
>   a smaller MF residual (Q3) means even a wallet-aware constraint would not
>   balance to the paisa.
> - **F3 (per-user linking) — CHANGED from the first write-up, which got this
>   backwards.** Keep the **per-login DCR the app already does** and store the
>   minted `client_id`/`client_secret` with the per-user refresh token. A
>   pre-registered client is *not* required: per-login registration is the only
>   auth path this codebase has ever used and it completes `/authorize` +
>   `/token` in production today (Q5). Open risk is volume, not viability —
>   nothing proves the server tolerates one registration per login at scale.
>
> **The one blocking unknown a human must weigh before M1 writes the
> `IND_STOCK` model:** `IND_STOCK` — the entire point of AlphaDesk — returned
> **zero holdings rows** on the operator's account, inside a payload envelope
> that shares almost no keys with the other asset types. **We have never seen an
> `IND_STOCK` holding row.** The snapshot confirms *why* — the account carries no
> `IND_STOCK` bucket at all (Q3), so this is an empty portfolio slice rather than
> a broken endpoint — but that does not make the row shape any less unknown.
> M1 can safely model `networth_snapshot` and the
> aggregator-shape holdings today, but any `IND_STOCK` row model would be
> invention. Recommended sequencing: build M1 against the verified shapes and the
> committed fixtures, keep the `IND_STOCK` row model behind an
> explicitly-unverified boundary, and re-run the capture against an account
> holding Indian stocks before D1 renders a holdings table.

## Notes / caveats

- **One account, one session.** Every "N of M" in the payload doc describes the
  operator's portfolio as captured on 2026-08-15. It proves what the API *did*,
  not what it will always do. The two places this matters most are `xirr`
  (0 in 14 of 14 here — but the vendor advertises it as populated) and
  `invested_amount` (0 missing here — but the vendor's own tool description says
  it is *often* missing for linked brokers, a case this account barely exercises).
- **The `IND_STOCK` gap is not closable from a desk.** It needs a linked account
  that actually holds Indian stocks. Until then
  `networth_holdings__IND_STOCK__populated.UNVERIFIED.json` is a hypothesis with
  a filename that says so.
- **SIP row shapes are unknown** (both tools returned zero rows), so no SIP
  fixture beyond the empty response was written. Inventing one would have been
  fiction dressed as a fixture.
- The `liabilities.loans` / `liabilities.credit_cards` element shapes are
  likewise unverified — both arrays were empty.
