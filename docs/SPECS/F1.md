# F1 — Persistence layer (identity tables, crypto, Alembic, pytest, tracing kill switch)

Branch: `v2-foundation` (off `main` @ `ddf138b`, post-C1).
Scope: **additive scaffolding only.** `git diff main -- backend/api backend/agents
backend/graph/graph.py backend/tools` is empty — no existing endpoint, agent or
tool changed behaviour, and nothing in `api/main.py` imports `db.*` yet.

What lands here is the floor the rest of v2 stands on: somewhere durable to put
a user and their broker link, a way to store OAuth material without storing it
in the clear, migrations, a test runner, and a way to run the future portfolio
graph without shipping anyone's holdings to LangSmith.

## Schema as built

Three tables. Portfolio holdings and daily snapshots are **deliberately absent**
— they belong to M1/S1, after the C2 data spike shows what IND Money actually
returns. Guessing at those columns now would mean migrating them twice.

### `users`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `varchar(255)` PK | The Clerk `user_id`. A string, not a UUID, so F2 adopts Clerk without a key migration. Pre-F3 rows use `user_id = "local"`. |
| `email` | `varchar(320)` null, indexed | |
| `created_at` | `timestamptz` not null | |

### `broker_links`

One row per (user, source). `source` is the connector key — `"ind_money"` today.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `integer` PK (serial) | |
| `user_id` | `varchar(255)` not null, indexed | FK → `users.id` **ON DELETE CASCADE** |
| `source` | `varchar(64)` not null | |
| `access_token_enc` | `varchar` null | Fernet ciphertext |
| `refresh_token_enc` | `varchar` null | Fernet ciphertext |
| `expires_at` | `timestamptz` null | access-token expiry |
| `client_id` | `varchar(255)` null | from dynamic client registration |
| `client_secret_enc` | `varchar` null | Fernet ciphertext |
| `token_url` | `varchar(2048)` null | endpoint to refresh against |
| `scope` | `varchar(1024)` null | |
| `supports_refresh` | `boolean` not null, default `false` | |
| `status` | `varchar(32)` not null, default `"active"` | link health |
| `linked_at` | `timestamptz` not null | |
| `last_refresh_at` | `timestamptz` null | |

`UNIQUE (user_id, source)` as `uq_broker_links_user_source` — re-linking updates
the row, it never accumulates a second one.

### `oauth_pending`

One in-flight authorization-code + PKCE flow, keyed by the OAuth `state`.

| Column | Type | Notes |
| --- | --- | --- |
| `state` | `varchar(255)` PK | the OAuth `state` parameter |
| `user_id` | `varchar(255)` not null, indexed | FK → `users.id` **ON DELETE CASCADE** |
| `source` | `varchar(64)` not null | |
| `verifier` | `varchar(255)` not null | PKCE `code_verifier` |
| `redirect_uri` | `varchar(2048)` not null | |
| `client_id` | `varchar(255)` null | |
| `client_secret_enc` | `varchar` null | Fernet ciphertext |
| `token_url` | `varchar(2048)` null | |
| `created_at` | `timestamptz` not null | |

**TTL 10 minutes, single use — enforced in application code (F3), not by the
DB.** The schema stores `created_at` and nothing else; there is no trigger, no
partial index and no expiry job. F3 must check the age and delete the row on
consumption. Written down here because a DB that silently keeps stale rows is
easy to mistake for one that expires them.

All timestamps are `timestamptz`, never naive `timestamp` — S1's 06:00-IST
calendar-day attribution cannot be done correctly on naive columns.

### Cascade semantics

Both child tables declare `ON DELETE CASCADE` **at the foreign-key level**
(`broker_links_user_id_fkey`, `oauth_pending_user_id_fkey`), verified in
Postgres as `pg_constraint.confdeltype = 'c'`.

That is a deliberate choice over an ORM `cascade="all, delete-orphan"`
relationship. The later "delete my data" card must be able to run
`DELETE FROM users WHERE id = ...` — from a migration, from psql, from a
background job that never loads the ORM — and have the dependent rows go with
it. An ORM-side cascade only fires when someone happens to use the ORM.
`tests/test_db_identity.py::test_deleting_a_user_cascades_to_links_and_pending`
proves it with raw SQL for exactly that reason.

There are no ORM `Relationship()` attributes on these models yet; add them when
a query needs them, not before.

## Crypto contract (`backend/db/crypto.py`)

- `encrypt(plaintext: str) -> str` / `decrypt(token: str) -> str`, Fernet
  (AES-128-CBC + HMAC-SHA256), keyed on env **`TOKEN_ENCRYPTION_KEY`**.
  `encrypt_optional` / `decrypt_optional` pass `None` through, for the nullable
  `*_enc` columns.
- **Every column named `*_enc` holds `encrypt()` output and nothing else.** A
  plaintext credential must never reach a column, a log line or an exception.
- Ciphertext is **non-deterministic** (random IV per call), so two users who
  linked with the same token do not produce matching rows.
- Ciphertext is **authenticated** — a tampered value raises rather than
  decrypting to garbage.
- The key is read **lazily, on first use**, not at import: the app still boots
  on a box with no key, and the failure surfaces the moment something actually
  tries to touch a credential. Missing key → `TokenEncryptionError` naming the
  variable and printing the generate-a-key one-liner. Invalid key → a distinct
  error that **does not echo the key**.
- The Fernet instance is cached per key *value*, so rotating the env var takes
  effect without a process restart.
- Key generation:
  `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`
- **Losing the key means every stored link is undecryptable and users must
  re-link.** It is a Space secret, not a config value.

Known gap, carried forward: `oauth_pending.verifier` is stored **in the clear**,
per the card's schema. It is a PKCE verifier — useless without the matching
authorization code, and the row lives at most 10 minutes — but if F3 wants
defence in depth, renaming it to `verifier_enc` is a one-column migration.

## Session / engine (`backend/db/session.py`)

- `DATABASE_URL` drives everything. `postgres://`, `postgresql://` and
  `postgresql+asyncpg://` all work — `async_url()` normalises the scheme, so an
  operator can paste a provider URL (Neon and Heroku hand out `postgres://`)
  verbatim. `sync_url()` is there for any tool that wants a plain DBAPI form.
- Engine and sessionmaker are lazy process-wide singletons;
  `async_session()` is the FastAPI dependency
  (`session: AsyncSession = Depends(async_session)`). It closes the session on
  the way out; committing is the caller's job. `dispose_engine()` is for
  shutdown/teardown.
- `pool_pre_ping=True` — serverless Postgres drops idle connections, and a
  stale pooled connection is the classic first production symptom.
- **Nothing here assumes Neon.** Any Postgres URL works; the local Docker
  container in `docs/TESTING/F1.md` is what F1 was verified against
  (ruling R3 — no Postgres is provisioned yet).

## Alembic (`backend/alembic/`, `backend/alembic.ini`)

**Decision: migrations run on the async engine (asyncpg), via
`connection.run_sync`.** The alternative — a sync driver such as psycopg2 used
only by Alembic — would mean a second Postgres driver in the runtime image, a
second URL form to keep in step with the first, and one more thing to get wrong
at 2am. One driver, one URL, normalised in one place.

- Run from `backend/`: `cd backend && alembic upgrade head`.
- URL precedence in `alembic/env.py:get_url()`: `-x db_url=...` → 
  `config.attributes["db_url"]` (how the pytest fixture targets the throwaway
  test DB) → `DATABASE_URL`. Always normalised to asyncpg.
- `alembic.ini` deliberately has **no `sqlalchemy.url`**, so migrations can
  never drift onto a different database than the app.
- `env.py` loads `backend/.env` (without overriding exported vars), so
  `alembic` needs no extra shell setup on a dev box.
- If a caller has already opened a connection and put it on
  `config.attributes["connection"]`, `env.py` reuses it instead of opening its
  own — that is what lets a test run a migration inside its own loop.
- One migration: `0001_initial_identity_tables.py`, autogenerated then reviewed.
  `alembic check` reports no drift against the models.
- `alembic` ships in the **runtime** requirements, not the dev ones: the Space
  needs to be able to run `alembic upgrade head` against production.

## Tracing kill switch (`backend/graph/portfolio_config.py`)

**Contract: every invocation of the future portfolio graph goes through
`portfolio_runnable_config()`, and produces no LangSmith trace — even when
`LANGCHAIN_TRACING_V2=true` is exported.** A1 must invoke its graph with it:

```python
from graph.portfolio_config import portfolio_runnable_config

result = await alphaDesk_portfolio_graph.ainvoke(
    state, portfolio_runnable_config(thread_id=run_id)
)
```

`callbacks` is an inheritable config key, so one config at the top covers every
nested node, tool and LLM call. The research pipeline is **unaffected** — it
keeps tracing normally; this switch is scoped to configs that carry it.

Optional kwargs: `thread_id` (goes into `configurable`), `run_name`, `tags`
(appended after `PORTFOLIO_TRACING_TAG`), `metadata`, `configurable`,
`recursion_limit`.

### Why it is built this way

Verified against langchain-core 1.4.9 / langsmith 0.10.3 — **there is no
`RunnableConfig` field that turns tracing off.** `RunnableConfig` allows exactly
`tags, metadata, callbacks, run_name, max_concurrency, recursion_limit,
configurable, run_id`, and `CallbackManager.configure()` decides whether to
attach a tracer from `langsmith.utils.tracing_is_enabled()` — a
contextvar/global/env lookup that never reads the config. Probed, not assumed:
with `LANGCHAIN_TRACING_V2=true`, `callbacks=None`, `callbacks=[]` and an empty
`CallbackManager` **all** resolve to a live `LangChainTracer`.
`tests/test_portfolio_config.py::test_empty_callbacks_are_not_enough` keeps that
fact honest.

The one seam `_configure()` leaves is its guard:

```python
if tracing_v2_enabled_ and not any(
    isinstance(handler, LangChainTracer) for handler in callback_manager.handlers
):
    ...attach a live LangChainTracer...
```

So the config ships `TracingDisabledTracer`, an inert `LangChainTracer`
subclass. It occupies the slot — no live tracer is ever constructed — and is
wired to receive nothing: every `ignore_*` flag is `True` (so `handle_event`
skips it for every callback category), `on_text` (the one unguarded event) is a
no-op, the trace-writing hooks are no-ops, and its LangSmith client is a null
object that *records* attempted calls instead of making them.

Two consequences worth knowing:

1. The resolved callback manager contains an object that **is** a
   `LangChainTracer` by `isinstance`. Assert on `is_tracing_disabled(config)` /
   `has_live_tracer(...)`, never on `isinstance`.
2. This rides on a langchain-core internal. **Re-run
   `tests/test_portfolio_config.py` after any langchain/langsmith bump** — that
   is exactly when it could rot. The suite includes a control case
   (`test_the_env_var_really_would_enable_tracing`) so a green run cannot mean
   "tracing was off anyway".

Because the Docker image resolves transitive deps freshly, it can carry a
different langchain-core than the dev venv (1.5.5 vs 1.4.9 at F1 time).
`backend/tests/check_tracing_in_image.py` re-proves the switch inside the image
without pytest — see `docs/TESTING/F1.md`.

asyncpg, alembic and Mako). The image still builds on `python:3.11-slim` with
no apt layer, and boots (`/docs` → 200).
