# S1 — Daily snapshots, capture job, staleness banner

Branch: `feat/portfolio-snapshots` (off `main` @ `6f493f4`, after D1).

**The one fact that shapes every decision below: a missed snapshot can never be
backfilled.** The IND Money MCP is point-in-time — it answers "what is your net
worth *now*" and nothing else. C2 confirmed no payload carries a date, there is
no historical endpoint, and no amount of durable storage invents a row for a day
the job did not run. Postgres makes a *stored* row safe; it cannot make an
*unacquired* one exist. So this card is designed against acquisition failure,
not storage failure, and every trade-off resolves the same way: write something
rather than nothing, and say so loudly when nothing was written.

---

## 1. Calendar-day attribution

### The rule

A capture is attributed to an **IST calendar day**, and any run before
**06:00 IST** is attributed to the **previous** IST calendar day.

One helper implements it — `services.snapshots.attributed_day(now)` — and
nothing anywhere derives a day from `date.today()`, from UTC, or from server
local time. The helper **refuses a naive datetime** rather than assuming a zone:
guessing is precisely how a snapshot lands on the wrong day, and a wrong day
cannot be corrected later.

### Why 06:00, and why calendar days at all

- The primary run is **23:45 IST**, after mutual-fund NAVs publish (~23:00). An
  earlier capture would pair today's equity prices with yesterday's NAVs and
  record a portfolio that never existed at any instant.
- The retry is **~01:00 IST**, which is a *different* calendar day. Without a
  cutoff it would file itself under tomorrow and the day it was rescuing would
  stay empty forever.
- GitHub cron is explicitly best-effort (`keepalive.yml` says so itself), so
  even the primary can slip past midnight IST. The same cutoff covers that.
- Calendar days rather than trading days deletes the NSE-holiday-calendar
  dependency entirely. A weekend capture is idempotent and harmless.

### IST is a fixed offset, not a zone

`IST = timezone(timedelta(hours=5, minutes=30))`, deliberately **not**
`zoneinfo.ZoneInfo("Asia/Kolkata")`. India has observed no daylight saving since
1945, so the offset is a constant — and depending on the tz database would make
attribution depend on whether the runtime image happens to ship one. A snapshot
landing on the wrong day because a slim container has no `/usr/share/zoneinfo`
is exactly the silent failure this card exists to prevent.

The frontend reproduces the same rule in
`frontend/components/portfolio/staleness.ts`, shifting the instant into IST and
reading **UTC** fields off the shifted value — never local ones, because the
reader's browser may be anywhere. Both sides have tests; change one, change both.

### Idempotency, and which capture wins

`UNIQUE (user_id, captured_on)`. A second capture on the same attributed day is
a **no-op that keeps the first row**.

That direction is the deliberate one. The 23:45 run is the one timed to sit
after the NAV publish, so it is the truest reading of that day; a 01:00 retry
re-reading prices that have since moved would overwrite a good number with a
worse one. **The retry exists to rescue a day with no row, not to improve one
that has one.**

It is enforced twice, for different reasons: a read first (cheap, and it means a
no-op retry spends **zero** source calls against a per-minute rate limit), and
the unique constraint second (correct, and it is what survives two runs racing).

## 2. Schema (migration `0002_snapshot_tables`)

```
snapshot_days      id | user_id FK→users ON DELETE CASCADE | captured_on DATE
                   | total_value NUMERIC(18,2) | currency | usd_inr_rate NUMERIC(18,6) NULL
                   | captured_at timestamptz        UNIQUE (user_id, captured_on)
snapshot_holdings  id | snapshot_id FK→snapshot_days ON DELETE CASCADE | source
                   | external_id | asset_type | symbol | isin | units | avg_cost
                   | invested_amount NULL | current_price | current_value | currency
snapshot_raw       id | snapshot_id FK→snapshot_days ON DELETE CASCADE | source
                   | payload JSONB | captured_at (indexed)     — pruned at 90 days
```

- **Every FK is `ON DELETE CASCADE` at the DB level**, verified in Postgres as
  `pg_constraint.confdeltype = 'c'`. L1's "delete my data" must work from psql
  or a migration, not only through the ORM — an unstated cascade on
  `snapshot_days` would either fail on the FK or leave a person's entire
  net-worth history behind after they asked for it to be erased.
- **`total_value` is the source's own headline total, passed straight through**
  and never recomputed. It is *not* the sum of `snapshot_holdings`, and nothing
  asserts that it is: the un-enumerable `US_STOCK_WALLET` bucket alone puts them
  ~2.3% apart, and adding it back does not close the gap (M1 §5). A test asserts
  the two are **unequal**, so a future "sanity check" adding equality fails first.
- **`invested_amount` stays NULL when unknown.** M1's rule survives into storage;
  a stored `0` would resurrect the fabricated ±100% return.
- **`snapshot_holdings` is a flat frozen copy**, not a FK into a positions table.
  A snapshot is a historical record, and a later rename, reclassification or
  delisting must not rewrite what was true on the day.
- The column list is the brief's, verbatim. `name` and `asset_type_raw` are
  deliberately absent; both are recoverable — the raw payload is in
  `snapshot_raw`, and for IND Money the asset-type string is the prefix of
  `external_id` (M1 §2).
- **`snapshot_raw.source` keeps meaning the connector key.** Which call a row
  came from lives *inside* the payload (`{"kind": "snapshot"|"holdings",
  "asset_type": …, "payload": …}`), so one column does not do two jobs. It is
  JSONB, so that is queryable.

`backend/db/models.py` gains the three tables; `users`, `broker_links` and
`oauth_pending` are unchanged.

## 3. The capture (`backend/services/snapshots.py`)

```python
capture_user(session, user_id, *, connector, now=None, fx=None, …) -> UserOutcome
capture_all(session, *, connector, user_ids=None, …)               -> CaptureReport
capture_if_missing(user_id, *, connector)                          -> UserOutcome | None
prune_raw(session, days=90)                                        -> int
history_points(session, user_id, days=90)                          -> [HistoryPoint]
last_captured_at(session, user_id)                                 -> datetime | None
```

### Source calls, and which ones are never made

1. `fetch_snapshot(user_id)` — one call, and the only one that matters. It
   carries `total_value`, which is what the history line is drawn from.
2. `fetch_holdings(user_id, t)` for each **non-empty** bucket the snapshot
   reported. Two filters, each saving a call that could only come back empty or
   refused:
   - **non-empty only** — a bucket the snapshot values at zero has nothing to
     enumerate. Walking the 16-member enum would spend most of a per-tool minute
     learning that 11 of them are empty (C2).
   - **never `UNKNOWN`** — IND Money reports buckets its own holdings endpoint
     refuses (`US_STOCK_WALLET`), so that call is a guaranteed
     `UnsupportedAssetType`. Its value is already inside `total_value` and its
     payload is already in `snapshot_raw`.

Calls are paced at `CALL_SPACING_SECONDS = 1.5`, including before the first
bucket (the snapshot call has just spent a unit of the same global budget). The
source allows 15/min per tool and 30/min globally; a capture makes 1 + *n* calls
and is comfortably inside both. The pacing is headroom, so a capture running
while somebody loads the dashboard does not push the pair over the line.

A `RateLimited` escaping the connector — which has *already* retried on the
source's own `retry_after` — buys one further wait (capped at 30s) and one
retry. After that the bucket is given up **for this run**, not the day.

### Degrade rules, and why each one goes the way it does

| Situation | Outcome | Reasoning |
| --- | --- | --- |
| `NotLinked` | `skipped`, no row | A lapsed account is a fact about that user, not an outage. Counting it as an error would leave the workflow permanently red and hide a real failure behind a standing alarm. |
| Any other `PortfolioSourceError` on the snapshot call | `failed`, **no row** | There is no `total_value`, so there is nothing worth storing. Critically it leaves **no row for a successful retry to collide with**. |
| A bucket fails or stays throttled | `captured`, row written, bucket listed in `buckets_failed` | A partial snapshot beats no snapshot. The figure the history is drawn from came off the snapshot call. |
| FX fetch fails | `captured`, `usd_inr_rate = NULL` | See §4. |
| An unexpected exception | `failed` for that user, batch continues | `capture_all` wraps every user; one user's failure never aborts the run. |

The batch is **serial**, not gathered: the source's rate limits are per account,
and a fan-out would trip them the moment there is more than one user.

`UserOutcome.reason` is always one of *our* fixed strings (`not_linked`,
`source_error`, …), never a source-supplied message — those can quote payload
fragments and this ends up in an HTTP response body.

### Who gets captured

`capture_users(session)` returns the distinct `broker_links.user_id`, and falls
back to the single constant `"local"` when there are none. That union is not a
guess about the future: it is what makes F3's cutover a data migration rather
than an edit to this function.

`_ensure_user()` upserts the `users` row (`ON CONFLICT DO NOTHING`) inside the
capture path. `snapshot_days.user_id` is a real FK, so without it the very first
capture on a fresh database fails on a constraint — and "run this INSERT once
before the cron starts" is a setup step somebody forgets on exactly the night it
matters.

## 4. USD/INR

`GET https://api.frankfurter.dev/v2/rate/USD/INR` (keyless, ECB reference;
shape `{date, base, quote, rate}`) → `snapshot_days.usd_inr_rate`.

**`fetch_usd_inr()` never raises.** DNS, timeout, 5xx, a reshaped body, a
non-numeric or implausible rate — every one degrades to `None` plus a log line.
The rate is display math for the US-exposure badge (M1 §4: holdings stay
vendor-INR and are **never re-summed** through it); the snapshot is data that
cannot be re-acquired. Trading the second for the first would be an obviously
bad bargain.

ECB publishes once per working day (~20:30 IST), so the 23:45 IST run gets
same-day data and a weekend run stores the most recent published rate — which is
the correct answer for a weekend, not a stale one: no rate was published.

The rate is fetched **after** the source calls and before the write, so an FX
outage costs a few seconds and nothing else.

## 5. Three nets on the same day

All three converge on one row through one idempotency key.

1. **23:45 IST cron** — the primary (§7).
2. **~01:00 IST cron** — the retry. A different calendar day, the same
   attributed one. Free when the primary worked.
3. **Opportunistic capture** — when `/portfolio/summary` is served and the
   current attributed day has no row, a capture is fired **after** the response
   is composed and never blocks it.

The third net exists because the first two can both stop without anyone being
told: GitHub disables scheduled workflows in a repo with no activity for 60
days, silently, and so does an expired secret or a renamed Space. The moment
somebody opens the dashboard is the moment the source can still be asked about
today, and that moment is too valuable to spend only on rendering.

Its guards:

- `_needs_capture(last_captured_at)` — one cheap comparison through the same
  `attributed_day` helper the writer files rows with, so the check and the write
  can never disagree. No task is scheduled when today already has a row.
- `single_flight(user_id)` — one capture per user per process at a time. It is
  **not** cluster-wide, and does not need to be: the unique constraint is the
  real guarantee and a second replica simply loses. This lock's job is the
  cheaper one, stopping a dashboard that fires several requests on load from
  making several identical bursts of source calls.
- Strong references to the background tasks are held (`asyncio.create_task`
  keeps only a weak one, and a garbage-collected capture would look exactly like
  a source that quietly stopped answering).
- The whole body is wrapped: a background net never breaks a page.

`POST /portfolio/capture` is the same path, **awaited** — someone who pressed a
button is owed an answer rather than a hopeful spinner — sharing the same
single-flight guard.

## 6. HTTP surface

### `api/routes/internal.py` — new router, **separate secret**

| Route | Guard | Returns |
| --- | --- | --- |
| `POST /internal/snapshot` | `x-cron-secret` == `CRON_SECRET` | `{captured_on, users_captured, skipped, errors, details[]}` |
| `POST /internal/prune?days=90` | same | `{deleted, days}` |

**Not behind the admin gate, deliberately.** Different caller, different secret,
different failure mode: `/portfolio/*` is guarded so a stranger cannot read the
operator's net worth; these are guarded so a stranger cannot make the backend
spend its source rate limit. A GitHub Actions runner is not an operator, and
giving it the admin secret would hand a CI system the ability to read holdings
and disconnect the account. Both directions are pinned by tests.

Fail-closed, with a deliberate split:

- `CRON_SECRET` **unset** → **503** `cron_not_configured`
- header absent or wrong → **401** `bad_cron_secret`

503 rather than 401 for the unset case because an operator staring at a red
workflow has to be able to tell "you never configured me" from "your secret is
wrong", and those are the two mistakes that actually get made. Compared with
`secrets.compare_digest`.

`/internal/snapshot` answers **200 with counts even when individual users
failed**. The workflow retries on 5xx; conflating "one account is unlinked" with
"the backend is down" would make it hammer a healthy server all night. The
workflow reads `errors` from the body instead (§7).

### `api/routes/portfolio.py` — three changes

- **`GET /portfolio/history`** now returns real points, `{date, net_worth}`,
  oldest first, money as strings like everything else on this surface. **No
  interpolation and no forward-fill**: a gap in the line is a day the job did
  not run, and smoothing it over erases the only evidence that it did not.
- **`GET /portfolio/summary`** carries `last_captured_at` (=
  `max(snapshot_days.captured_at)`, unwindowed) and fires the third net.
- **`POST /portfolio/capture`** — new, on the same admin gate as the reads,
  backing the top bar's button.

**All three degrade to "no history" rather than 500 when there is no database.**
`optional_session` yields `None` when `DATABASE_URL` is unset, and query
failures are caught and logged. The live figures on this dashboard come from the
source; S1 must not have turned an additive feature into a hard dependency. Two
tests pin that.

### Retention

Normalized rows and daily totals: **forever**. They are small, they are the
actual history, and they cannot be re-acquired. `snapshot_raw`: pruned at 90
days by `prune_raw`, which refuses a window under one day (`days=0` would delete
everything captured tonight).

## 7. `.github/workflows/snapshot.yml`

Modelled on `keepalive.yml`, but deliberately louder.

| Cron (UTC) | IST | Job |
| --- | --- | --- |
| `15 18 * * *` | 23:45 | capture (primary) |
| `30 19 * * *` | 01:00 next day | capture (retry, same attributed day) |
| `45 19 * * 0` | Sunday | prune raw > 90 days |

Each capture run: check configuration → wake the Space (poll `/` for 200, up to
~6 min) → `POST /internal/snapshot` with retry/backoff.

- **Retries only what a retry can fix.** 5xx and dead connections back off
  15/30/60s across 4 attempts. **401/403** (wrong secret) and **503** (backend
  has no `CRON_SECRET`) fail immediately — they will be just as wrong in 30
  seconds, and one honest error beats six identical ones.
- **A 200 whose body reports `errors > 0` fails the run.** The request
  succeeding is not the same as the day being captured.
- **Missing configuration fails**, where `keepalive.yml` warns and exits 0. A
  keepalive that skips a run costs a cold start; a snapshot that skips a run
  costs a day that cannot be recovered, and a green tick on a job that silently
  did nothing is the exact failure this card exists to prevent. *Consequence:
  merging before the secrets are wired produces red runs — disable the workflow
  from the Actions tab until the runbook in `docs/TESTING/S1.md` is done.*
- The **60-day scheduled-workflow-disable landmine** is documented in the file's
  header, together with the reason the staleness banner exists rather than
  trusting this file to keep running.

## 8. Frontend

- **`components/portfolio/staleness.ts`** — pure date logic, no React, no fetch,
  reproducing the backend's cutoff exactly. Three states:

  | State | Condition | Banner |
  | --- | --- | --- |
  | `never` | nothing ever captured | **none** |
  | `fresh` | newest capture ≥ last expected day | none |
  | `stale` | newest capture < last expected day | amber `WarnBanner` |

  `lastExpectedDay(now) = attributedDay(now) - 1 day`, and that one-day trail is
  the load-bearing part. While the current attributed day is `A`, `A`'s own
  capture runs at 23:45 IST — near the end of that window — so expecting it
  would light the banner every morning at breakfast. A banner that cries wolf
  daily is one the reader stops seeing, which costs more than the extra day of
  latency buys. (It also means a stale gap is never reported as "1 days ago".)

  `never` renders **nothing** on purpose: the trend card already says history
  starts with the first snapshot, and stacking a warning on an accurate empty
  state reads as a fault where there is none. An unparseable timestamp is
  treated as `never` too — diagnosing "history paused" from a value we could not
  read would be inventing a diagnosis.

- **`components/portfolio/StalenessBanner.tsx`** — `WarnBanner`'s first caller
  (D1 built it for exactly this and left it unused). Rendered **above** the stat
  cards: if the history has stopped accruing, the reader needs to know that
  before they read a trend drawn from it.

- **`PortfolioTopBar`** — "Capture snapshot" loses its `soon` badge and calls
  `POST /portfolio/capture`. A second press says *"Already captured today"*
  rather than pretending to work, because the first capture of a day is
  deliberately the one that is kept.

- **`NetWorthTrend`** — unchanged except that its subtitle now prints the
  **attributed day** rather than the raw `last_captured_at`. A capture that ran
  at 01:00 IST belongs to the previous day, and its wall-clock time would
  contradict the last point on the axis beside it. (It also keeps a
  microsecond-precision ISO string out of a card subtitle — a defect that was
  invisible while `last_captured_at` was always `null`.)

- **`lib/api.ts`** — `capturePortfolioSnapshot()`, and `portfolioFetch` gained an
  optional method so a POST can share the gate handling.

## 10. What S1 deliberately does not do

- **No reconciliation between `total_value` and the holdings rows.** They differ
  by construction (M1 §5) and a test asserts they differ.
- **No backfill, and no synthesized points.** There is nothing to backfill from.
- **No per-user scheduling.** One batch, serial, because the rate limits are per
  account.
- **No cluster-wide lock.** The unique constraint is the guarantee; the
  in-process lock is only a rate-limit courtesy.
- **No new dependency.** `httpx` was already a direct requirement; the frontend
  adds four dev-only packages (`vitest`, `jsdom`, `@testing-library/react`,
  `@testing-library/dom`) and no runtime one.
- **No production wiring.** No Neon exists yet. The 10-minute operator runbook
  is in `docs/TESTING/S1.md` §7.
