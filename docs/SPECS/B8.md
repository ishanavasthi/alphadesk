# B8 — Top movers over a user-chosen period (backend)

Branch: `ishanavasthi/b8-movers-backend` (off `main` @ `038633c`). Issue #66.

Answers "which of my holdings moved the most between date A and date B?" from
the **captured daily snapshots** — the first feature that reads
`snapshot_holdings` for anything. No source call is made at request time, which
is why a five-year window costs the same as a one-day one.

Framing (`V2_PLAN.md` §8.3): **descriptive arithmetic over the user's own
captured history.** It ranks what did happen. It rates nothing, recommends
nothing, projects nothing.

**The one fact that shapes every decision below: the history is a record of
readings, not of transactions.** Two snapshots tell you what a position was
worth on two days. They do not tell you why it changed — a rally, a top-up, a
partial sell and a throttled bucket all look identical in a value column. Every
rule in §2 exists to stop the endpoint from asserting a market move it cannot
actually see.

---

## 1. Schema (migration `0007_snapshot_holding_name`)

```
snapshot_holdings  … | asset_type | name TEXT NULL | symbol | isin | …
```

One nullable column, chained off the current head `0006`. (Issue #66 says
"off 0005"; it was written before `0006_portfolio_cache` landed. One head is the
invariant — the lineage follows the repo.)

**Why the column exists at all.** A display name lives in exactly one place
today: `snapshot_raw.payload…rows[].investment`. `snapshot_raw` is **pruned at
90 days**; `snapshot_holdings` is kept forever. A name kept only in the raw
payload therefore evaporates off a holding whose history survives, and the card
degrades into a list of `EQUITY:INDS00577`.

- **Nullable, and it stays nullable.** Rows captured before this migration have
  no name and never will — their raw payload may already be gone. The source
  also returns an empty label on some rows (M1 normalizes that to `None`).
- **`TEXT`, not a bounded string.** A name is decoration; a capture is
  unrepeatable. A source that one day returns a 300-character fund name must
  not be able to fail a snapshot with a length violation.
- Populated at capture time in `services.snapshots._holding_row`, straight off
  `Holding.name` — the connector already carries it.

**Read-path fallback for pre-migration rows.** Where a joined row has no `name`,
the movers query scans that window's `snapshot_raw` payloads and matches
`investment_code` against the code half of `external_id`
(`"<raw_type>:<code>"`). Ids of the hashed form `"<raw_type>:h:<hash>"` match
nothing on purpose — they exist precisely because the source gave no code, and
an approximate match would be a guessed name. **Pruned + pre-migration rows
render `name: null`**: an honest nameless row, never a guess.

## 2. The four bases — the honest-data core

`services.snapshots.movers_report()` joins the two days on **`(source,
external_id)`** — M1's identity pair — and classifies every joined key:

| `basis` | When | Where it lands | `change_pct` |
|---|---|---|---|
| `price` | non-null `units` **and** `current_price` on **both** days | `gainers` / `losers` | from `current_price` |
| `balance` | present both days, unpriced (SA, FD, cash) | `flows` | `null` |
| `opened` | present on the later day only | `opened` | `null` |
| `closed` | present on the earlier day only | `closed` | `null` |

### `change_pct` comes from the price, never the value

`(end.current_price − start.current_price) / start.current_price × 100`,
quantized to `0.01`.

Taking it from `current_value` is the single way this card could lie about
someone's money: a top-up would read as a rally and a partial sell as a crash.
The regression case is in the suite — a holding whose value doubles while its
price falls 10% must appear among the **losers**.

`change_abs` is still `end.current_value − start.current_value` — the real rupee
delta, which is what a reader wants in the ₹ column. It is the *percentage*, and
therefore the *ranking*, that must stay off the value.

A `start_price` of `0` yields `change_pct: null`: a percentage off zero is
undefined, not infinite, so the row is simply unranked.

### Balances are flows, not movers

An unpriced row's delta is a deposit or a withdrawal. On real data
(2026-08-21, 5 captured days) the largest rupee movers were a savings account
(+₹16.5k) and an FD top-up, while the largest *percentage* mover was a ₹0.94
US-stock fraction. Both columns are needed and neither list may contain the
other's rows — hence `flows` as its own labelled group.

### Opened and closed are never ±100%

A position seen on one day only has no return to state. Rendering it as ±100% is
the fabricated figure M1 spent a card eliminating. Both `change_abs` and
`change_pct` are `null` on these rows; the endpoint reports only that the
position appeared or left.

This includes the honestly-empty bucket: FD returning `{"rows": []}` on
2026-08-18 with `buckets_failed` **NULL** means the deposit really is gone, and
`closed` is the true answer.

### A failed bucket is *unknown*, not empty

If an asset type appears in `snapshot_days.buckets_failed` on **either** compared
day, every row of that type is dropped from **every** list and the bucket is
named in `excluded`. Reporting a holding as `closed` because the bucket listing
it was throttled would tell someone they sold funds they still own — the worst
sentence this endpoint could write.

### The join key is not `symbol`

`symbol` is NULL on every IND Money mutual-fund and savings row (the source keys
instruments by its own code and publishes no ticker). Joining on it would
collapse an entire bucket into one line.

## 3. Window snapping

- `to` omitted → the latest captured day. `from` omitted → 7 attributed days
  before `to`.
- `compared.from` = earliest captured day ≥ `requested.from`;
  `compared.to` = latest captured day ≤ `requested.to`. Both are bounded
  *inside* the requested window — the window is snapped **inwards**, never
  widened, and a gap is never interpolated.
- When `compared` differs from `requested`, `note` says so and names the two
  days actually compared.
- `compared.from >= compared.to`, or either side missing → **200** with empty
  lists and a note. One captured day is not a comparison, and there is no
  honest way to manufacture the second one: the source is point-in-time, so a
  day nobody captured has no answer.

## 4. `GET /portfolio/movers`

```
GET /portfolio/movers?from=YYYY-MM-DD&to=YYYY-MM-DD&limit=N
```

On the existing `/portfolio` router, so it inherits the router's identity
(`portfolio_identity` — a verified Clerk token, or `"local"` in single-tenant
dev; **401** with neither) and the app-wide per-caller rate limit
(`api/ratelimit.py`). `limit` caps each of `gainers` and `losers`
independently — default 5, max 50. **Presets (1D/1W/1M/3M/YTD) are a frontend
concern; the API takes dates.**

```json
{
  "requested": {"from": "2026-08-16", "to": "2026-08-20"},
  "compared":  {"from": "2026-08-16", "to": "2026-08-20"},
  "note": null,
  "gainers": [], "losers": [], "flows": [], "opened": [], "closed": [],
  "excluded": [{"asset_type": "MF", "reason": "bucket failed on 2026-08-18"}],
  "limit": 5,
  "currency": "INR"
}
```

Each entry:

```json
{"source": "ind_money", "external_id": "EQUITY:INDS00577", "asset_type": "EQUITY",
 "name": "Mover Ltd", "symbol": null, "basis": "price",
 "start_price": "200", "end_price": "240",
 "start_value": "1000", "end_value": "1200",
 "change_abs": "200", "change_pct": "20.00", "currency": "INR"}
```

**Money is serialized as strings**, like every other figure on this surface
(`_num`) — `name`, `symbol` and the prices are nullable, and `change_pct` is
null wherever the basis is not price-computable.

### Degradation

Identical to `GET /portfolio/history`, and for the same reason: this dashboard's
live figures do not depend on Postgres and must not start doing so here.

- `DATABASE_URL` unset (`optional_session` yields `None`) → **200**, empty
  lists, `compared: {from: null, to: null}`, and a note saying no database is
  configured.
- Any query failure → **200** with a note, logged at warning. Movers are
  additive; they never fail the page.
- **401 is the one hard failure**, and it is the identity gate, not the data.

## 5. Scope

Owned here: `db/models.py` (`SnapshotHolding.name`),
`alembic/versions/0007_snapshot_holding_name.py`, `services/snapshots.py`
(capture-time `name`, the movers section), `api/routes/portfolio.py`
(`GET /movers`), `tests/test_movers.py`.

Explicitly **not** touched: `agents/`, `graph/`, `tools/`,
`api/routes/{overview,account,internal}.py`, `api/deps.py`, the Lab pages, and
the requirements files (**no new dependencies**).

Out of scope by the issue: flow *attribution* (why cash moved — **B1**), XIRR
(**B2**), the treemap (**B6**), any AI narration of movers, and any new source
call at request time.
