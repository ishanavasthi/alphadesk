Everything below runs on a laptop with Docker. **No Neon exists yet**; nothing
in S1 assumes one, and §7 is the operator runbook for wiring production after
this branch merges.

### `tests/test_snapshots.py` (33 tests, needs Postgres)

| What it pins | Why it would be silent otherwise |
| --- | --- |
| `test_attribution_cutoff_on_both_sides` | 23:45 IST → that day, 01:00 IST → previous. **Both** scheduled runs must fill the *same* day or the retry is useless. Boundary asserted at 05:59 and 06:00. |
| `test_attribution_is_ist_not_utc_and_not_server_local` | Pins the **zone**, not just the schedule. Note that neither scheduled run discriminates on its own — both fall the same side of the IST *and* UTC cutoffs. The two assertions that do the work are **02:00 UTC** (07:30 IST, past the cutoff → the IST day; a UTC helper with the same cutoff answers the day before) and **00:15 UTC** (05:45 IST, before it; a plain UTC date answers the day after). Between them they kill both wrong implementations — verified by mutating `astimezone(IST)` to `astimezone(utc)`, which fails on the 02:00 line. |
| `test_attribution_refuses_a_naive_datetime` | A naive datetime would be attributed from whatever the server thinks the time is. |
| `test_last_expected_day_trails_by_one` | The banner threshold. |
| `test_capture_writes_the_day_its_holdings_and_its_raw` | Day + holdings + one raw row per call, `total_value` equal to the source's own total. |
| `test_capture_creates_the_user_row_it_needs` | The FK. A missing `users` row fails the very first capture on a fresh DB. |
| `test_two_runs_on_the_same_attributed_day_make_one_row` | **The idempotency headline.** |
| `test_the_first_capture_of_a_day_wins` | The 23:45 reading is not overwritten by a 01:00 one. |
| `test_a_second_run_does_not_spend_source_calls` | The retry costs zero calls against a per-minute limit. |
| `test_only_non_empty_buckets_are_enumerated` | Never the full 16, never `UNKNOWN`, never a duplicate. |
| `test_totals_are_not_asserted_against_the_holdings_sum` | Asserts they **differ**, so a future "sanity check" adding equality fails here first. |
| `test_an_unreadable_bucket_still_writes_the_day` | A partial snapshot beats no snapshot. |
| `test_a_partial_capture_leaves_queryable_evidence` | **The partiality outlives the response body.** Without the stored marker, a day with an unreadable bucket and a day where that bucket was genuinely empty are byte-identical, and "you held nothing there" is a false statement no later query could correct. |
| `test_a_clean_capture_leaves_no_marker` | NULL, not `[]` — and it really is SQL NULL. Written after this test caught a JSONB `null` being stored (reads back as `None` in Python while being `IS NOT NULL` in SQL), which made `WHERE buckets_failed IS NOT NULL` match every clean day. |

| `test_an_unsupported_bucket_is_not_fatal` | A gap in the rows, not a lost day. |
| `test_a_dead_link_is_skipped_not_failed` | **A revoked link must not turn the workflow red forever.** |
| `test_a_source_outage_is_an_error_and_writes_nothing` | |
| `test_a_non_unique_constraint_failure_is_not_reported_as_already_captured` | Only a losing race on `(user_id, captured_on)` may report `already_captured`. Any other `IntegrityError` is a bug, and filing it under the one status nobody investigates would make the run look like a free no-op while the day silently never got written. Forced with a holdings row pointing at a non-existent snapshot id, so the failing constraint is a FK. |
| `test_the_batch_records_that_failure_instead_of_swallowing_it` | ...and `capture_all` surfaces it as `errors: 1`, not a skip. |
| `test_a_failed_attempt_leaves_no_row_for_the_retry_to_collide_with` | **The 502-then-success case**, asserted where the code is: a failed attempt must not leave a partial row that idempotency then refuses to replace. (The workflow's own bash retry is exercised in §5.) |
| `test_fx_failure_stores_null_and_still_writes_the_row` | |
| `test_fetch_usd_inr_never_raises` | Driven through the real function with a broken transport, not by trusting the `except` to be reachable. |

### `tests/test_snapshots_api.py` (18 tests)

The gate group needs no database — the point is that it refuses before anything
expensive happens:

- every internal route × {no header, wrong header} → **401**;
- a **non-ASCII** `x-cron-secret` → **401, not 500**. `secrets.compare_digest`
  raises `TypeError` on any `str` above U+007F and Starlette decodes headers as
  latin-1, so one high byte used to produce an unhandled 500 — a worse answer
  and a free liveness oracle. Sent as raw bytes, because httpx refuses to encode
  such a header from a `str` (which is why no test had ever reached that code).
  Mutation-checked: restoring the `str` comparison fails both cases with
  `TypeError`.
- `CRON_SECRET` unset → **503 `cron_not_configured`** (fail-closed, and
  distinguishable from a wrong secret);
- `DATABASE_URL` unset → **503 `no_database`**. A Space with a cron secret and
  no database is a real half-finished deployment; without this the engine raised
  on first use and the workflow saw an opaque 500 it would retry four times
  against a backend that cannot succeed;
- **the admin secret does not open `/internal`, and the cron secret does not
  open `/portfolio`** — both directions, so the two gates cannot become one.

The route group runs against the migrated test database through an ASGI client:
capture + idempotency end-to-end, a user-level failure arriving as a **200 body**
rather than a 5xx the workflow would retry, `/portfolio/history` returning real
points as strings, `/portfolio/summary` carrying `last_captured_at`, the
admin-gated capture button, and the prune route leaving the history intact.

Two tests in `tests/test_api_portfolio.py` cover the no-database degrade
(`/history` empty with a note, `/summary` with `last_captured_at: null`) — never
a 500.

## 5. The workflow's retry logic, run for real

The bash in `.github/workflows/snapshot.yml` is the thing that turns a sleeping
Space into a captured day, so it is executed verbatim rather than read. Point a
throwaway HTTP server at it that answers 502 *N* times and then 200, extract the
step with `yaml.safe_load`, and run it with `BACKEND_URL` / `CRON_SECRET` in the
environment. Observed:

| Scenario | Result |
| --- | --- |
| 502, 502, 200 | `retrying in 15s` → `retrying in 30s` → `HTTP 200`, `::notice::Snapshot for … 1 captured.`, **exit 0** |
| 502 × 4 | 15 / 30 / 60 s backoff, `::error::Snapshot trigger failed after 4 attempts`, **exit 1 (red)** |
| wrong secret (401) | fails on attempt 1 with no retries — it would be just as wrong in 30 s |
| 404 / 422 | fails on attempt 1, naming `BACKEND_URL` as the likely cause |
| **503 `cron_not_configured`** | fails on attempt 1: the Space has no cron secret |
| **503 `no_database`** | fails on attempt 1, pointing at step 3 of the runbook |
| **503 with no app-level `code`** | *"503 with no app-level code; treating as transient"* → **retried** |
| **dropped connection** | logs `HTTP 000` — not `000000` (curl prints `000` itself, so the old `\|\| echo 000` fallback concatenated) |
| platform 503 → dropped conn → 502 → 200 | all three retried, `exit 0` on the fourth attempt |
| `BACKEND_URL` and `CRON_SECRET` unset | `::error::Not configured: …`, **exit 1** |

**Why the 503 split matters.** The wake step polls `/` until 200 before the
trigger runs, so a trigger-phase 503 is *usually* app-level — but "usually" is
not a guarantee: a Hugging Face edge can answer 503 after a healthy 200, and
short-circuiting every 503 would let one hiccup cost the night. Status alone
cannot tell the two apart, so the loop reads `detail.code` off the body:
`cron_not_configured` and `no_database` are deployments that cannot succeed no
matter how often we ask, and anything else is treated as transient and retried.

**Timeout arithmetic** (`timeout-minutes: 40`), because the final retry must
never be killed by the job clock — a killed retry is a permanently lost day:

| Step | Worst case |
| --- | --- |
| wake | 420 s deadline + ≤ 20 s curl overshoot ≈ **7.5 min** |
| trigger | 4 × 300 s curl + 15 + 30 + 60 s backoff ≈ **21.8 min** |
| total | ≈ **29.3 min**, inside 40 with headroom |

The wake loop is **deadline-based rather than attempt-based** for exactly this
reason: an attempt loop's real budget is `attempts × (timeout + sleep)`, which
is not the number anyone reads off it — the previous 24-attempt version claimed
"~6 minutes" in its own error text and could run for 18. Measured against a dead
port: **422 s elapsed against a declared 420 s budget**, and the error message
now quotes the budget it actually keeps.

`bash -n` over every `run:` block, and `yaml.safe_load` over the file, both pass.
(The 503 body is parsed with a `python3 -c` one-liner, not a heredoc: an
unindented heredoc body terminates the YAML block scalar — which it did, once.)

## 7. Operator runbook — wiring production (10 minutes)

Do this **after** merging. Order matters: the workflow fails loudly on missing
configuration, so wire the backend before the schedule can fire.

**1 — Provision Postgres (~3 min).** Any Postgres works; Neon is the plan.
Create a project and copy the connection string. It will look like
`postgresql://user:pw@ep-xxx.neon.tech/db?sslmode=require&channel_binding=require`
— **paste it verbatim**, F1's `normalize_url()` translates it for asyncpg.

**2 — Generate the cron secret (~10 s).**

```bash
openssl rand -base64 32
```

**3 — Space secrets (~2 min).** In the Hugging Face Space → Settings →
Variables and secrets, add as **secrets**:

| Name | Value |
| --- | --- |
| `DATABASE_URL` | the string from step 1 |
| `CRON_SECRET` | the string from step 2 |

`TOKEN_ENCRYPTION_KEY` and `ALPHADESK_ADMIN_SECRET` should already be there
(F1, C0). `ALPHADESK_SINGLE_TENANT` must stay **unset**.

**4 — Run the migration (~2 min).** The Space image ships `alembic` for exactly
this. Either open a terminal on the Space and run it, or run it from a laptop
against the same URL:

```bash
cd backend
DATABASE_URL="<the string from step 1>" alembic upgrade head
```

Confirm: `Running upgrade -> 0001`, then `0001 -> 0002` and `0002 -> 0003`,
and a second run is a
no-op. **This step repeats for every future deploy that ships a migration.**

**5 — GitHub Actions (~2 min).** Repo → Settings → Secrets and variables →
Actions:

- **Variables** tab: `BACKEND_URL` = the Space root, e.g.
  `https://<user>-alphadesk.hf.space` (already set for `keepalive.yml`).
- **Secrets** tab: `CRON_SECRET` = the **same** string as step 2.

**6 — Prove it (~1 min).** Actions → *snapshot* → **Run workflow**. It should
wake the Space, POST, and print
`::notice::Snapshot for <date>: N captured.` Then load `/portfolio` with the
admin header and confirm `last_captured_at` is set and no banner shows.

If it fails, the error text names the cause:

| Message | Fix |
| --- | --- |
| `Not configured: BACKEND_URL… CRON_SECRET…` | step 5 |
| `Rejected (401)` | the two `CRON_SECRET`s differ — steps 3 and 5 |
| `Backend has no CRON_SECRET configured` (503) | step 3, then restart the Space |
| `Backend never answered 200` | the Space is down or the URL is wrong |
| 200 but `errors: 1` | the IND Money link is broken; reconnect via `POST /auth/login` with the admin header |

**7 — Diarise the 60-day landmine.** GitHub disables scheduled workflows in a
repo with no activity for 60 days. The staleness banner is the backstop; when it
appears, check the Actions tab first. Days missed in between are gone.
