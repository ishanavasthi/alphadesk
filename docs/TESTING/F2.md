# F2 — how to run and verify Clerk identity

**No Clerk account is needed for anything in §1–§3.** That is the point of this
card's test design: a Clerk session token is an ordinary RS256 JWT, so the suite
mints its own key pair and serves its own JWKS. §4 is the operator runbook for
the handful of things only real keys can prove.

## 0. One-time setup

```bash
source .venv/bin/activate                        # repo-root venv
pip install -r requirements.txt -r requirements-dev.txt
cd frontend && npm install
```

### How the JWKS mock works

`tests/test_auth_deps.py` stands up a complete fake Clerk instance in three
pieces:

1. **A real RSA key pair**, generated per session with `cryptography`. Tokens are
   signed with the private half by `jwt.encode(..., algorithm="RS256")`.
2. **A JWKS document** built from the public half with
   `RSAAlgorithm.to_jwk(...)`, plus the `kid` / `use` / `alg` fields Clerk
   publishes.
3. **`PyJWKClient.fetch_data` monkeypatched** to return that document and count
   how often it is called.

Patching `fetch_data` rather than the whole client is deliberate: it leaves
`PyJWKClient`'s own caching in the picture, which is what
`test_jwks_is_fetched_once_and_then_verification_is_networkless` asserts — five
verifications, one fetch. Swapping the client for a stub would have made that
test vacuous.

The patched callable is bound to the fake-server object *before* it is installed
on the class, so `PyJWKClient` calling `self.fetch_data()` lands on it with no
arguments. (Installing an unbound method here fails with a confusing
`missing 1 required positional argument`.)

### What the rejection cases cover, and why each one

| Test | The thing it stops |
|---|---|
| `test_alg_none_is_401` | A token asking to be trusted with no signature. Hand-assembled from base64 pieces rather than produced by `jwt.encode`, because a library refusing to *emit* one says nothing about whether we would *accept* one. |
| `test_hs256_signed_with_the_public_key_is_401` | Algorithm confusion. The public key is public; treating it as an HMAC secret lets anyone mint tokens. |
| `test_token_signed_by_another_key_is_401` | A token with the *right* `kid` and the wrong signer. |
| `test_unknown_kid_is_401` | A `kid` that is not in the key set. |
| `test_expired_token_is_401` / `..._not_yet_valid_...` | `exp` and `nbf`. |
| `test_wrong_issuer_is_401` / `test_missing_issuer_is_401` | A token from a different Clerk instance. |
| `test_missing_sub_is_401` / `test_blank_sub_is_401` | A verified token that identifies nobody. |
| `test_wrong_azp_is_401_when_configured` | CSRF via a token minted for another origin — checked only when `CLERK_AUTHORIZED_PARTIES` is set. |
| `test_unconfigured_clerk_is_503_not_401` | An unconfigured server telling the caller *their* token is bad. |
| `test_an_unreachable_jwks_endpoint_is_503_not_401` | Same, for a Clerk outage. A 401 here sends a signed-in user off to re-authenticate against the service that is down. |

### The one that is easy to write wrongly

`test_the_row_is_written_once_not_once_per_request`. A second
`INSERT … ON CONFLICT DO NOTHING` is invisible in a row count, so counting rows
proves nothing. Instead:

1. three requests → exactly one `users` row;
2. delete the row with raw SQL;
3. a fourth request → the row **does not** come back (so no INSERT was issued);
4. `deps.reset_seen_users()`, a fifth request → the row *is* back.

Step 4 is what makes step 3 mean "the cache did its job" rather than "the insert
is broken".

Also worth knowing: `test_first_sight_creates_the_users_row` asserts
`created_at` is set and timezone-aware. `User.created_at`'s default lives on the
*model*, and a Core insert never consults it — the column is `NOT NULL`, so
omitting it is not a slightly-wrong timestamp, it is an `IntegrityError` on
every user's first sign-in. It was caught exactly this way.

### Manual smoke test, still with no Clerk account

```bash
cd backend
python - <<'PY'
import json, time, jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa
from jwt.algorithms import RSAAlgorithm

key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
pem = key.private_bytes(serialization.Encoding.PEM,
                        serialization.PrivateFormat.PKCS8,
                        serialization.NoEncryption())
jwk = json.loads(RSAAlgorithm.to_jwk(key.public_key()))
jwk.update({"kid": "local", "use": "sig", "alg": "RS256"})
open("/tmp/jwks.json", "w").write(json.dumps({"keys": [jwk]}))

now = int(time.time())
print(jwt.encode({"iss": "https://local.invalid", "sub": "user_local",
                  "iat": now, "exp": now + 3600},
                 pem, algorithm="RS256", headers={"kid": "local"}))
PY
```

Serve `/tmp/jwks.json` on any local port, point `CLERK_JWKS_URL` at it, set
`CLERK_ISSUER=https://local.invalid`, and the printed token will verify.

### Visual identity, and the trap in checking it

`/` **cannot** be compared by screenshot hash: the top bar's "Live" dot and the
connection spinner are CSS animations, so two screenshots of one unchanged build
already differ. The procedure that works:

1. Screenshot `/` and `/portfolio` from a build of the pre-branch tree.
2. Screenshot both again from this branch with the flag off.
3. Diff pixel-by-pixel, recording **count and bounding box**.
4. Screenshot `/` twice from the *same* build, ~1 s apart, and diff those too.

`/portfolio` renders no `TopBar` (see `TerminalChrome`), so it is static and must
come out at **0 differing pixels** — it did. `/` came out at 230 differing
pixels inside bounding box `[374, 18, 1231, 534]`; the same-build self-diff was
242 pixels inside the *identical* box. Same box, same magnitude ⇒ the page's own
animations, not the change.

Also diff the served HTML with chunk hashes and the Next build id normalised
away. The rendered element tree must be identical; the only permitted
differences are `<script>` tags in `<head>` and the Flight payload.

### What the vitest suites assert

`tests/auth-flag.test.tsx` mocks `@clerk/nextjs` and `next/dynamic`, then
re-imports each module under test after `vi.resetModules()` + `vi.stubEnv` —
`AUTH_ENABLED` is read at module scope, so a top-level import would pin whatever
value the runner started with.

- `AUTH_ENABLED` is true for `"true"` and false for `"1"`, `"yes"`, `"TRUE"`,
  `""` and unset.
- `<Identity>` flag-off renders children with **no** `<ClerkProvider>` and never
  calls it; flag-on wraps the children *inside* it (a provider rendered as a
  sibling would type-check, render, and quietly hand every hook below it the
  signed-out answer).
- `<UserMenu>` flag-off renders nothing **and `next/dynamic` is never called**,
  so the chunk cannot be requested by any path.
- `withAuth` returns the caller's headers *by identity* when off or signed out,
  merges `Authorization: Bearer …` when on, keeps the C0 admin header, and
  survives a getter that throws.

`tests/auth-boundaries.test.ts` scans the source, because what it protects *is*
the shape of the source:

- zero `import { useAuth } from ".../AuthProvider"` anywhere;
- `@clerk/nextjs` imported only from `components/clerk/` and `middleware.ts` —
  with a **positive control** asserting the detector finds the files that *do*
  import it, so a broken regex cannot report "all clear" forever;
- every `API_BASE` call site in `lib/api.ts` goes through `apiFetch`.

## 3. Frontend — the flag is on, with placeholder keys

The key must be *syntactically* valid (`pk_test_` + base64 of
`<host>$`) or Clerk refuses at build time. This one decodes to
`placeholder-f2.clerk.accounts.dev$`:

```bash
cd frontend
export NEXT_PUBLIC_AUTH_ENABLED=true
export NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_cGxhY2Vob2xkZXItZjIuY2xlcmsuYWNjb3VudHMuZGV2JA==
export CLERK_SECRET_KEY=sk_test_00000000000000000000000000000000000000000
npm run build          # must succeed
npx next start -p 3111
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3111/sign-in   # 200
```

**What you can verify this way:** the build compiles with Clerk mounted; the
middleware runs (`x-clerk-auth-status: signed-out`, `x-clerk-auth-reason:
dev-browser-missing` on the response); `/sign-in` and `/waitlist` are 200
instead of 404; the server-rendered HTML references `clerk-js` and the
configured Frontend API host.

**What you cannot:** anything visual. Open `/` in a browser with these keys and
the page is replaced by Clerk's error JSON —

```json
{"errors":[{"message":"Invalid host","code":"host_invalid"}]}
```

— because a `pk_test_` key makes `clerk-js` run its dev-browser handshake, which
*navigates the browser* to the Frontend API. The server is fine (200, correct
HTML); the takeover is client-side. **Flag on ⇒ real keys.** Never deploy the
flag on with a placeholder.

## 4. Once real Clerk keys exist

### 4a. Backend, against the live JWKS

```bash
cd backend
export CLERK_JWKS_URL="https://<frontend-api>/.well-known/jwks.json"
export CLERK_ISSUER="https://<frontend-api>"
export CLERK_AUTHORIZED_PARTIES="https://<your-frontend-origin>"

curl -s "$CLERK_JWKS_URL" | head -c 200      # must be a JWKS, not a 404 page
```

Mind the `.json` — a production custom domain serves the JWKS *only* at
`/.well-known/jwks.json`, while a `*.clerk.accounts.dev` dev domain also answers
`/.well-known/jwks`. A URL that works in dev can 404 in production.

Grab a real token from a signed-in browser (devtools console, on the frontend
with the flag on):

```js
await window.Clerk.session.getToken()
```

Then, with the backend running:

```bash
python - <<'PY'
import os
from api.deps import verify_token
print(verify_token(os.environ["TOKEN"])["sub"])   # -> user_...
PY
```

Expected `user_…`. Then confirm it fails closed:

- edit one character of the token → `HTTPException(401)`;
- unset `CLERK_ISSUER` → `HTTPException(503)`;
- wait past `exp` (~60 s) and retry → 401.

### 4b. Frontend, end to end

1. Clerk Dashboard → Configure → Restrictions → Sign-up mode → **Waitlist**.
2. Build and serve with the real `pk_live_`/`sk_live_` pair and
   `NEXT_PUBLIC_AUTH_ENABLED=true`.
3. `/waitlist` renders the join form; submit and confirm the email arrives.
4. `/sign-in` renders the sign-in card, and its "no account?" link points at
   `/waitlist` (that is `<ClerkProvider waitlistUrl>`).
5. Approve the waitlist entry in the Dashboard, follow the invite, sign in.
6. Top bar shows the `<UserButton>` avatar; signing out returns to `/`.
7. In devtools → Network, a `/portfolio/summary` request now carries both
   `Authorization: Bearer …` and the C0 `x-alphadesk-admin-secret` header. Both
   is correct until F3 removes the second.

### 4c. Turning it off again

Set `NEXT_PUBLIC_AUTH_ENABLED=false` and **rebuild**. It is inlined at build
time; restarting alone changes nothing. Re-run §2 to confirm you are back to the
pre-F2 site.
