# C2 — testing, re-capture, and the leak check

Companion to [`docs/SPECS/C2.md`](../SPECS/C2.md) and
[`docs/ind_money_payloads.md`](../ind_money_payloads.md).

Three procedures live here:

1. [Re-running the capture](#1-re-running-the-capture) against a live account.
2. [Validating the fixtures](#2-validating-the-fixtures).
3. [The leak check](#3-the-leak-check) — the gate that must pass before anything
   from a capture session is committed.

---

## 1. Re-running the capture

⚠️ **The output of this procedure is real financial data. It must never touch
the repo.** Capture into a scratch directory outside the working tree, keep it
only as long as the review needs it, and delete it once the card's verification
and human gate have both passed (see [When you are done](#when-you-are-done)).

### Prerequisites

- The repo-root venv: `source /Users/ishan/Desktop/code/alphadesk/.venv/bin/activate`
  (needs `mcp==1.28.1` — `mcp` 2.0.0 removed `streamablehttp_client`).
- `backend/.env` with `IND_MONEY_MCP_URL` set.
- A live link: `backend/.ind_money_token.json` (gitignored). The auth module
  auto-refreshes the hourly access token from the stored refresh token, so a
  token file from an earlier session is usually enough. If it is not, reconnect
  via `POST /auth/login` with the `x-alphadesk-admin-secret` header (C0 gate)
  and open the returned URL.
- **Never commit `.ind_money_token.json`, and never copy it anywhere tracked.**

### Choose a scratch directory outside the repo

```bash
export C2_CAPTURES="${TMPDIR:-/tmp}/c2-captures-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$C2_CAPTURES"
echo "$C2_CAPTURES"      # must NOT be under the repo root
```

The leak check refuses to run if the captures directory is inside the repo —
that situation *is* the leak.

### What to call

Reproduce the original probe set (72 calls). Drive the MCP session the way the
app does — `tools.ind_money_auth.get_access_token()` for the bearer token,
`streamablehttp_client` + `ClientSession`, and `tools.ind_money._unwrap` /
`._extract_text` to get past the `{"result": "<stringified JSON>"}` wrapper that
every tool on this server uses. Write one JSON file per call, named
`<tool>__<args>.json`, into `$C2_CAPTURES`.

The five steps below are **68 MCP operations** and produce **68 capture files**
(the inventory plus one payload file per tool call). With the 4 probe calls in
the next section that is **72 calls** in total.

| Step | Calls |
| --- | --- |
| 1 | `list_tools` → save the full inventory with input schemas to `tool_inventory.json`. **Reconcile the enums against this doc before proceeding** — the `asset_type` list below is what the server returned in Aug 2026, not a constant. |
| 2 | `networth_snapshot()` |
| 3 | `networth_holdings(asset_type=X)` for **every** value of the server's `asset_type` enum: `IND_STOCK, MF, US_STOCK, BOND, EPF, NPS, SA, FD, CRYPTO, INSURANCE, VEHICLE, RE, RD, AIF, PMS, PPF` (16) |
| 4 | `networth_allocation_breakdown(asset_type=X, breakdown_by=Y)` for the full cross-product with `Y ∈ {assets, sector, market_cap}` (48) |
| 5 | `mf_sips()`, `indian_stocks_sips()` |

Practical notes from the original run:

- **Pace the calls — the server rate-limits, and it will not tell you in a
  header.** The original write-up blamed session timeouts for the batching; the
  real constraint is a **global per-minute rate limit** (observed: 30 per
  minute, `scope: "global"`), and `networth_allocation_breakdown` costs **2**
  units per call rather than 1. The 68-operation sequence therefore consumes
  well over 100 units, and a naive tight loop trips the limit partway through.
  Re-authenticating and opening a fresh `ClientSession` every ~12 calls also
  helps with long-session stability, but pacing is what actually makes the run
  complete.
- **A throttled call still returns `isError: false`.** The body is replaced by
  a `rate_limit_exceeded` envelope (see `ind_money_payloads.md` §2.5), so a
  harness that only checks `isError` will happily write a "successful" capture
  file containing an error. **Check for an `error` key in the unwrapped body**
  and back off by `retry_after_seconds`, or the capture set will be silently
  full of holes.
- Wrap each call in `asyncio.wait_for(..., timeout=90)` and record failures as
  `{"is_error": true, "error_text": …}` rather than aborting the run.
- Record the arguments alongside the payload — the response echoes `asset_type` /
  `breakdown_by`, but only for some tools.

**`tool_inventory.json` format matters to the leak check.** Write it as either
a bare JSON array of tool objects, `[{...}, {...}]`, or wrapped as
`{"tools": [{...}]}` — the checker accepts both. Each element keeps its `name`
and `inputSchema`, because that is what seeds the structural allowlist (tool
names and enum members are published on purpose). A dump in any other shape
silently contributes nothing to the allowlist, and the check then floods with
false positives against ordinary vocabulary in the docs.

### DCR probe (question 5)

⚠️ **This is the one probe with a side effect, so do not re-run it casually.**
Every `POST /register` mints a **real OAuth client on the vendor's server**,
which persists — no `registration_access_token` was ever captured, so we have
no revoke or expiry path. Re-running it to re-create a lost capture file is not
worth it; the capture from the original run was deliberately left unrestored
for exactly this reason. Skip this section unless the question genuinely needs
a fresh registration, and note that `begin_login()` already exercises DCR on
every login if all you need is proof that repeat registration works.

```
GET  <issuer>/.well-known/oauth-authorization-server   → discovery doc
POST <registration_endpoint>  × 2, each with a fresh random client_name
```

- Send the registration POST **with no auth header** — that is the point of the
  probe, and it is how the real flow behaves.
- Record for each attempt: HTTP status, whether `client_id` / `client_secret`
  came back (as **booleans**, never the values), the response key names, and any
  `Retry-After` / `X-RateLimit-*` / `RateLimit-*` headers.
- **Do not log out, revoke, or invalidate the existing client or token.** Adding
  registrations is safe; removing one is not.
- Also run an **unauthenticated `list_tools`** as a control — it should fail,
  which is what proves `/register` being open is a property of `/register` and
  not of the whole server.

### When you are done

**Keep the captures until the card clears its gate, then delete them.** They
are the only evidence a reviewer can check the published counts against, and
the first C2 review round did exactly that — it re-derived the reconciliation
arithmetic in Q3 and found the doc's stated root cause incomplete. Deleting
them at the moment of commit makes every claim in the payload doc unfalsifiable.

So: retain in the scratch directory (never in the working tree) until **both**
the verification pass and the human gate are done, then

```bash
rm -rf "$C2_CAPTURES"
```

Do this **every time**, including when the run failed partway. Whoever is
driving the card owns the deletion; it is not optional and it is not deferred
past the gate.

## 2. Validating the fixtures

The committed fixtures are pure data, so they are validated by
`backend/tests/test_ind_money_fixtures.py` (64 tests, no network, no DB, no
application imports — they run anywhere in well under a second).

```bash
cd backend
pytest tests/test_ind_money_fixtures.py -q
```

Expected: `64 passed`.

Full suite (for the record — C2 added 64 tests and changed nothing else):

```bash
cd backend
pytest -q          # 101 passed, 6 skipped   (was 43 passed, 6 skipped before C2)
```

The 6 skips are F1's Postgres tests skipping loudly without a database; see
`docs/TESTING/F1.md`.

### What those tests actually guard

Two different things, and the second is the one that matters over time:

1. **Shape fidelity** — holdings rows carry exactly the documented 14 keys,
   `IND_STOCK` fixtures carry the 19-key live-trading envelope, breakdown files
   carry the right discriminator per `breakdown_by`, the raw-envelope fixture
   still unwraps, snapshot totals reconcile internally
   (`total_networth == total_current_value − liabilities.total`).
2. **Edge-case preservation** — the missing / `null` / `0` `invested_amount`
   rows, the zero-value holding, the empty `broker`, the empty `investment`, the
   `int`/`float` mixture, and `xirr == 0` everywhere. These exist precisely
   because they are ugly, and ugly things get "cleaned up" by well-meaning
   future edits. The tests fail loudly if they disappear.

There are also two negative tests worth knowing about, because they encode
findings rather than shapes:

- `test_no_currency_or_date_field_anywhere` — fails if any fixture invents a
  `currency` / `as_of` / date field. The real payloads have none, and a fixture
  that grew one would quietly license code that depends on it.
- `test_snapshot_carries_the_unenumerable_wallet_bucket` — fails if
  `US_STOCK_WALLET` is ever added to the holdings `asset_type` enum in the
  fixture set. That gap is a finding (Q3), not a typo to fix.

A worked example of these tests earning their keep: the first version of
`test_mf_fixture_keeps_every_invested_amount_edge_case` used
`row.get("invested_amount") is None` to count the null row and failed with
`assert 2 == 1` — because `.get()` cannot tell a **missing key** from an
**explicit null**. The fixture was right and the assertion was wrong. That is
exactly the bug the fixture exists to provoke in M1's parsing code, and it
provoked it in the test first.

## 3. The leak check

**This is the gate. Nothing from a capture session gets committed until it
passes.** The repo is public, and eyeballing a 68-file capture set against a
16-file fixture set does not scale and does not work.

```bash
python3 backend/tests/leak_check_ind_money.py --captures "$C2_CAPTURES"
```

Exit `0` = clean, `1` = leak found, `2` = usage error.

### What it does

1. **Harvests a secret corpus from the raw captures** — every leaf string value
   (length ≥ 4) and every numeric value (floats, plus integers ≥ 1000; smaller
   integers are counts and flags, not account data).
2. **Subtracts the structural allowlist** — JSON *key* names (field names are
   published on purpose), tool names, and the input-schema enum members
   (`asset_type`, `breakdown_by`, …). Four capture files seed this allowlist
   instead of the secret corpus, because they contain no account data by
   construction: `tool_inventory.json` (vendor schema and English prose),
   `probe_dcr.json` (the OAuth discovery document plus status codes — the probe
   recorded credentials as booleans only, and its RFC 8414 vocabulary like
   `authorization_code` / `S256` / `client_secret_post` is quoted deliberately
   in Q5), `probe_unauth_list_tools.json` (an exception type from a call
   that returned no data), and `_capture_index.json` (the harness manifest —
   file names, tool names, arguments and a shape summary, no leaf value, and a
   type vocabulary of `float`/`str` that would otherwise false-positive against
   every type annotation in the payload doc).
3. **Scans every staged file, wherever it lives**, plus every tracked file
   under `docs/` and `backend/tests/`, for overlap:
   - strings, case-insensitively, at **every** occurrence — not just the first,
     so fixing one hit cannot mask another;
   - numbers on **token boundaries**, so a real `1337` is not "found" inside an
     invented `113370` (bare-substring matching produced ~40 such false
     positives and buried the real signal);
   - plus **exact numeric equality** on parsed JSON, which catches a leaked
     value that got reformatted (`1234.50` vs `1234.5`).
4. **Reports hits without ever printing a capture value.** A hit reads
   `file :: line-or-json-path :: kind :: sha1=xxxxxxxx len=N :: from <capture files>`.
   The location tells the author which of *their own* (synthetic) fields is
   colliding; the provenance tells them whether it came from account data or
   from a schema file. The tool that just found a secret does not then print it.

### Proving the check is not vacuous

A leak check that can never fail is worse than none, so run the self-test:

```bash
python3 backend/tests/leak_check_ind_money.py --self-test --captures "$C2_CAPTURES"
```

It plants one real capture string and one real capture number into a temp file
outside the repo, scans it, and requires **both** to be caught. Output:

```
SELF-TEST planted string caught: True
SELF-TEST planted number caught: True
SELF-TEST: PASS — the scanner detects planted capture values, so a PASS on the
real files is meaningful.
```

The canary file is deleted whether it passes or fails.

### The procedure actually used before committing C2

1. Wrote the payload doc and all 16 fixtures by hand from the shape notes.
2. `git add` everything (the check scans staged + tracked files, so unstaged
   fixtures would have been silently skipped — stage first, then check).
3. Ran the check. **It failed five times, and each failure was real work:**

   | Round | Hits | What it caught |
   | --- | --- | --- |
   | 1 | 18 | Mostly OAuth-vocabulary false positives from `probe_dcr.json`, **plus two genuine leaks**: the payload doc had reused a real `assetclass_l2` label in its prose. |
   | 2 | 6 | Same two real strings at their remaining occurrences (this is what motivated match-every-occurrence). |
   | 3 | 46 | Fixtures now in scope: four **real vendor classification labels** reused as fixture placeholders, plus ~40 numeric-substring false positives. |
   | 4 | 2 | One invented aggregate happened to **exactly equal** a real captured value — a coincidence, changed anyway. |
   | 5 | 1 | This very document: an illustrative "a real X is not found inside an invented Y" example had used a real captured number as X. |

4. Fixed each round at the source: reworded the doc, renamed every
   classification placeholder to an unmistakably synthetic one
   (`Fixture Cap Band A`, `Fixture Growth Assets`, …), and re-derived the one
   colliding number while keeping the fixture's internal arithmetic consistent.
5. Re-ran to `PASS`, ran `--self-test` to confirm the PASS meant something, ran
   the fixture tests, then committed.
6. **Adversarial review then found a sixth leak the passing check could not
   see** — a capture value quoted in a comment inside
   `leak_check_ind_money.py` itself, which the check skipped because its scan
   scope was `docs/` plus the fixtures directory and nothing else. Fixed by
   rewording the comment *and* widening the scope (every staged file, plus all
   of `docs/` and `backend/tests/`), and the branch's history was rewritten so
   no commit ever carried the value. Round 5 above is the same class of bug
   caught one file earlier.
7. Kept the captures until the gate; deleted them after.

Two lessons worth carrying into any future capture. **The check will flag your
own generic-sounding placeholders**, because vendor taxonomy labels are generic
by nature — the fix is not to allowlist them, it is to make fixture values
obviously synthetic. Anything in a fixture that could plausibly be real is
either a leak or indistinguishable from one. And **a leak check is only as wide
as its scan scope**: a `PASS` means nothing about files the tool never opened,
so widen the scope before you trust the green.

### If it fails

Fix the fixture or the doc. **Do not** add the token to the allowlist to make
the check green — the allowlist is for field names and schema enums only. If you
genuinely believe a flagged token is structural, say why in the commit message
and add it to the constants at the top of the script with a comment, the way
`SCHEMA_ONLY_FILES` documents its four entries.
