# B10 — how to run and verify manual fixed deposits (backend)

Everything below runs on a laptop with Docker. Spec: `docs/SPECS/B10.md`.

## 0. Local Postgres

The DB tests need a real Postgres — the container from `docs/TESTING/F1.md`:

```bash
docker run --rm -d --name b10-pg \
  -e POSTGRES_PASSWORD=test -e POSTGRES_DB=alphadesk \
  -p 5433:5432 postgres:16
```

Without it the DB-backed tests **skip loudly** rather than failing. **Never
point the suite at Neon** — the conftest guard (`resolve_test_database_url`)
refuses a non-loopback `DATABASE_URL`, because the fixture runs
`DROP DATABASE … WITH (FORCE)`. Tear down with `docker rm -f b10-pg`.

## 1. Migration

```bash
cd backend
DATABASE_URL="postgresql+asyncpg://postgres:test@localhost:5433/alphadesk" \
  alembic upgrade head
```

Expected tail on a database already at `0007`:

```
INFO  [alembic.runtime.migration] Running upgrade 0007 -> 0008, manual fixed deposits
```

Run it again — it must be a **no-op** (no `Running upgrade` line). Then:

```bash
DATABASE_URL="…/alphadesk" alembic heads   # -> 0008 (head)     one head, not two
DATABASE_URL="…/alphadesk" alembic check   # -> No new upgrade operations detected.

docker exec b10-pg psql -U postgres -d alphadesk -c '\d manual_fds'
#  principal   | numeric(18,2)            not null
#  rate_pct    | numeric(9,4)             not null       never float
#  compounding | character varying(16)    not null
#  "manual_fds_user_id_fkey" FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
```

`alembic downgrade -1` drops the index and the table cleanly, and
`upgrade head` puts them back.

## 2. Backend tests

```bash
cd backend && pytest
```

**794 passed, 1 skipped** on the B10 tip — 732 before this card, plus its 62.
The one skip is `test_overview_live.py`, opt-in behind `RUN_OPENAI_LIVE=1` and
unrelated to this card — **no DB test may skip**; if they do, the container in
§0 is not running.

The two new files:

- `tests/test_manual_fd.py` — 18 tests, **pure**: no database, no HTTP, no app.
- `tests/test_api_manual_fd.py` — 44 tests over the real ASGI app against the
  throwaway Postgres, with the `StubConnector` standing in for IND Money.

Run just this card:

```bash
cd backend && pytest tests/test_manual_fd.py tests/test_api_manual_fd.py -q
```

### Why the fixtures look the way they do

- **Matured deposits are used wherever an exact figure is asserted.** Accrual
  freezes at maturity, so `100000 @ 8% quarterly, 2025-01-01 → 2026-01-01` is
  worth `108243.22` today, tomorrow and in 2040. A running deposit would make
  every expected number drift with the date the suite happens to run on.
- **The vendor side is `StubConnector`**, a real second connector reading the
  invented portfolio in `tests/fixtures/demo/` — no network, no credential, and
  it already contains one vendor FD, which is what makes "manual rows sit
  *alongside* vendor rows" testable.
- **S1's opportunistic capture is defanged** (`schedule_capture_if_missing` →
  no-op). Left alone it writes snapshot rows mid-test and moves
  `last_captured_at` between two reads that are supposed to be comparable.
- **`as_of` is excluded from the byte-identical comparisons.** It is the
  connector's own fetch stamp (M1 rule 3: no date comes from a payload), so it
  legitimately differs between two forced re-reads. Everything else must not.

## 3. The claims, and the test that pins each

### The math (`tests/test_manual_fd.py`)

Every expected figure is hand-computed and shown as the arithmetic beside it.

| Claim | Test |
|---|---|
| quarterly: `100000 × 1.02^4 = 108243.22` | `test_quarterly_over_one_year` |
| monthly: `100000 × 1.01^12 = 112682.50` | `test_monthly_over_one_year` |
| half-yearly: `100000 × 1.05^2 = 110250.00` | `test_half_yearly_over_one_year` |
| yearly: `100000 × 1.10 = 110000.00` | `test_yearly_over_one_year` |
| simple: `200000 × (1 + 0.06×2) = 224000.00` over 730 days | `test_simple_interest_over_two_years` |
| simple and compound are genuinely different paths (`1.10 < 1.1025 < 1.1047…`) | `test_simple_and_compound_diverge_on_the_same_terms` |
| an unknown convention raises rather than guessing a frequency | `test_unknown_compounding_raises_rather_than_guessing` |
| a partial period uses a fractional exponent: 182 days → `104028.71` | `test_partial_period_uses_a_fractional_exponent` |
| …and always sits between the whole periods it straddles | `test_a_partial_period_sits_between_the_periods_it_straddles` |
| **a deposit that has not started has earned nothing** | `test_a_deposit_that_has_not_started_has_earned_nothing` |
| the year fraction is 0 before the start and never negative | `test_year_fraction_is_zero_before_the_start_and_never_negative` |
| **the value freezes at maturity** — four years later it is unchanged | `test_value_freezes_at_maturity_and_never_accrues_past_the_term` |
| `matured` flips on the maturity date itself, `days_to_maturity` hits 0 | `test_matured_flips_on_the_maturity_date_itself` |
| `days_to_maturity` floors at 0, never negative | `test_days_to_maturity_floors_at_zero` |
| `accrued_interest == current_value − principal` at every point in the term | `test_accrued_interest_is_always_value_minus_principal` |
| `maturity_value` does not depend on `as_of` | `test_maturity_value_is_the_same_number_whenever_it_is_asked_for` |
| every figure is a `Decimal` quantized to paise | `test_every_figure_is_a_decimal_and_quantized_to_paise` |
| **there is no `float` anywhere in the module** — AST scan of the source | `test_the_module_contains_no_float_anywhere` |

That last one is the acceptance criterion enforced against the source itself. A
single `float(...)` would reintroduce the binary rounding M1 spent a card
eliminating, and it would be invisible — a float answer looks right to two
decimal places until the day it does not.

Plus the extensions to the existing exhaustive assertions, which are the ones
that fail first if a future card forgets this table:

- `tests/conftest.py` — `manual_fds` added to `_ALL_TABLES` (truncated between
  tests).
- `tests/test_db_identity.py` — `manual_fds` added to the "exactly these tables
  and nothing else" set.
- `tests/test_api_portfolio.py` — `/portfolio/fds` added to the `ROUTES` tuple,

- `tests/test_account_deletion.py` — a `ManualFd` row is seeded and `ManualFd`

## 4. Manual check against a running backend

Single-tenant dev, with the Postgres from §0:

```bash
cd backend
export DATABASE_URL="postgresql+asyncpg://postgres:test@localhost:5433/alphadesk"
ALPHADESK_SINGLE_TENANT=1 uvicorn api.main:app --reload --port 8000
```

```bash
# 1. Add a deposit that has already matured — its value is fixed forever.
curl -s localhost:8000/portfolio/fds -H 'content-type: application/json' -d '{
  "label": "HDFC Bank FD", "principal": "100000", "rate_pct": "8",
  "compounding": "quarterly", "start_date": "2025-01-01",
  "maturity_date": "2026-01-01"}' | python -m json.tool
# current_value 108243.22, accrued_interest 8243.22, matured true, days_to_maturity 0

# 2. Edit the rate; the accrual moves on the very next read.
curl -s -X PATCH localhost:8000/portfolio/fds/<id> \
  -H 'content-type: application/json' -d '{"rate_pct": "10"}' | python -m json.tool
# current_value 110381.29     (100000 x 1.025^4)

# 3. It is in the FD bucket, labelled, next to whatever the vendor said.
curl -s 'localhost:8000/portfolio/holdings?asset_type=FD' | python -m json.tool
# one row with "source": "manual", the vendor rows untouched beside it

# 4. And in the summary's additive block — with net_worth unchanged.
curl -s localhost:8000/portfolio/summary | python -m json.tool | grep -A3 '"manual"'

# 5. Delete it.
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE localhost:8000/portfolio/fds/<id>   # 204
```

What to look at, in order:

1. `current_value` against the terms by hand. `100000 × 1.02^4` is checkable on
   a phone calculator; if it does not reconcile, the formula regressed.
2. `matured` / `days_to_maturity` — a past-dated deposit must read `true` / `0`,
   never a negative countdown or a value still climbing.
3. `/portfolio/holdings?asset_type=FD` — the manual row and the vendor row are
   both there, and the vendor one is **untouched**. This card does not repair
   the vendor's FD number (that is B9/#65).
4. `/portfolio/summary` — `net_worth` is *exactly* what it was before the
   deposit existed, and `manual.total` sits beside it. A changed `net_worth`
   would mean the additive rule broke.

To see the no-database behaviour, restart uvicorn with `DATABASE_URL` unset:
`GET /portfolio/fds` answers `200` with a note, and `POST` answers `503
{"code": "no_database"}`.

## Frontend

Run: `cd frontend && npm test` (vitest; `tests/manual-fds.test.tsx`, 15 cases)
and `npm run build` + `npx tsc --noEmit` for the compile gates.

By hand, on a running stack (backend single-tenant + stub source is enough —
see the backend sections above): open `/portfolio`, and walk the states that
matter —

1. **Empty state** — the card invites the first add; provenance caption in the
   header names AlphaDesk, not IND Money, as the source.
2. **Add** — bad input first (negative principal, rate 99, maturity before
   start): three inline field errors, no request fired. Then a real deposit:
   the row appears without a reload and the net-worth stat gains the
   `incl. ₹X in N manual FDs` subline.
3. **Matured** — add a deposit whose maturity is past: amber `Matured` badge,
   "value frozen", `days_to_maturity` never negative.
4. **Edit** — change the rate; the accrued value on the row changes on save.
   The arithmetic is checkable on a phone calculator (backend §4).
5. **Delete** — confirm dialog, row gone, footer total and stat subline follow.
6. **Privacy toggle** (eye, top bar) — every rupee masks to `₹••••••`; rates,
   dates and labels stay readable.
7. **375 px** — no horizontal scroll; rows stack.

All seven were pixel-verified 2026-08-21 (headless Chrome over the real app,
screenshots in the session scratchpad — the repo stays binary-free).
