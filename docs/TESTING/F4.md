# F4 — Testing

## What runs, and against what

- **Backend:** `cd backend && pytest`. **625 passed** on the F4 tip (613 at F3
  + 12 new in `tests/test_api_lab_f4.py`; `test_db_identity.py`'s table-set
  assertion gained `watchlist`). The DB tests need a real Postgres — the local
  Docker container from `docs/TESTING/F1.md`:

  ```bash
  docker run --rm -d --name alphadesk-f4-pg \
    -e POSTGRES_PASSWORD=test -e POSTGRES_DB=alphadesk \
    -p 5433:5432 postgres:16
  ```

  Without it the DB-backed F4 tests skip loudly. **Never point the suite at
  Neon** — the conftest guard (`resolve_test_database_url`) refuses a
  non-loopback `DATABASE_URL`, and it stays.
- **Frontend:** `cd frontend && npm test` → **64 passed** (63 + `lab-label`).
  `npx tsc --noEmit` clean; `npm run build` green.
- **Migration:** `alembic upgrade head` applies `0005`, is **idempotent** (a
  second run is a no-op), `alembic check` reports **no drift**, `downgrade -1`
  drops the table cleanly, and the FK is `confdeltype = 'c'` (CASCADE) in
  Postgres.

The MCP and the graph are **mocked** for the gating tests (a `FakeGraph` that
streams two nodes with no LLM/MCP behind it, and an `auth_status` stub that
decides which users read as linked) — the brief's "mock the MCP for the gating
tests". The database is real.

## The claims, and the test that pins each

| Claim | Test |
|---|---|
| `/analyze` with no identity → **401**, and the graph never runs (no ambient fallback) | `test_analyze_without_identity_is_401` |
| `/analyze` for an identified-but-unlinked user → **409** ("link your account"), graph never runs | `test_analyze_for_an_unlinked_user_is_409` |
| `/analyze` for a linked user **runs**, is stamped with the caller, binds them as the run identity | `test_analyze_runs_for_a_linked_user` |
| the run-user binding is reset after the run (a later userless call is ambient, not the last caller) | `test_analyze_binding_does_not_leak_after_the_run` |
| user B reading user A's analysis / run status → **404, not 403** | `test_one_user_cannot_read_anothers_analysis`, `..._run_status` |
| user B approving user A's run → **404**, and the graph does **not** resume | `test_one_user_cannot_approve_anothers_run` |
| `/analyses` lists only the caller's runs | `test_analyses_lists_only_the_callers` |
| the watchlist survives a simulated restart with its thesis intact and its opaque `run_id` degrading to "no longer available" | `test_watchlist_survives_a_restart_with_thesis_and_a_dead_run_link` |

## Live checks (two Clerk test users)

Isolation across two real Clerk identities is what an attacker actually tests.
Mint two throwaway users with the `clerk` CLI on the dev instance, sign in as
each on a flag-on build (or drive their session tokens through ASGI as the suite
does), and confirm:

1. a stubbed Lab run created for user A does not appear in user B's `/analyses`;
2. user B fetching A's `/analysis/{run_id}` gets a 404, not A's payload;
3. each user's watchlist is their own.

Properties 1–3 are pinned by the pytest suite above against the same
two-signed-in-users setup (`clerk_stub.bearer` mints a valid session token per
`user_id`); the live pass with real Clerk users is the belt-and-braces the F3
runbook established. **Delete the throwaway users from the Dashboard afterwards.**

## The one thing a mock can't prove

A **real IND-backed `/analyze`** — that a linked run mints from the caller's own
`AuthStore` end-to-end and returns recommendations. Documented as a morning item
in `docs/MORNING.md` (run in single-tenant dev after a real IND login, or signed
in on a flag-on build). Not a blocker: the mocked gating path is green.
