# Testing F3 — per-user broker linking

Three layers, and they answer different questions:

1. **pytest** — is the logic right? 586 tests, 68 of them new.
2. **A live run against the real Clerk instance** — do two real users, with two
   real browser-minted session tokens, actually see only their own link? 24
   checks, all passing.
3. **A morning checklist** (§6) — the one thing that could not be done
   overnight: a real IND Money login, because the operator's link is revoked at
   the source and only they can re-establish it.

**What is mocked, and why.** Only the IND Money OAuth endpoints. `/register`
mints a live OAuth client on the vendor's server, `/token` burns a one-use
authorization code, and `/revoke` kills a grant a human would have to
re-establish by hand — none of those belongs in a test run, and C2 already
declined to re-run its own DCR probe for the same reason. Everything else is
real: real Clerk, real Postgres, real Fernet, the real app.

---

## 1. Running the suite

```bash
docker run --rm -d --name alphadesk-f3-pg \
  -e POSTGRES_PASSWORD=test -e POSTGRES_DB=alphadesk \
  -p 5433:5432 postgres:16

source .venv/bin/activate
cd backend && pytest                       # 586 passed
```

Without a Postgres the DB tests skip loudly rather than fail. **The suite
creates and DROPs a `<db>_test` database**, so `conftest.resolve_test_database_url`
refuses to inherit a non-loopback `DATABASE_URL` — the Neon URL in
`backend/.env` cannot be reached by a test run unless somebody deliberately puts
it in `TEST_DATABASE_URL`. That guard is load-bearing; leave it alone.

New fixture: **`db_env`** (`tests/conftest.py`) points the *application's* engine
at the throwaway test database and yields a sessionmaker. `db_session` gives a
test its own session, which is not enough for code whose whole point is that it
opens its own — `AuthStore` reads and writes a `broker_links` row from wherever
the request happens to be.

### What the new files cover

| File | Tests | The claims |
|---|---|---|
| `tests/test_ind_money_auth.py` | 23 | encryption at rest (checked in **SQL**, not through `decrypt()`); state single-use + TTL; the callback links the *state's* owner; cross-user isolation; per-user locks; revoke-before-delete; client reuse and re-registration on a moved redirect; both scopes; PKCE; `revoked` vs transient; the ambient sources authenticate nobody outside single-tenant dev. |
| `tests/test_adoption.py` | 15 | right email adopts once; wrong email never; no email never; unset variable never; idempotent; a collision never overwrites the signed-in user's row; only a **verified primary** address counts; a stranger never becomes the admin identity. |
| `tests/test_api_auth_f3.py` | 30 | the same isolation over HTTP against `api.main.app`; `/auth/login|logout` reject the admin header and anonymous callers; a bad token never falls through to the admin path; the interim admin path before and after adoption; a replayed or forged `state` links nothing; the callback error page never echoes the broker; `/auth/status` registers the identity. |
| `tests/test_auth_deps.py` (+8) | 50 | `sid` required; 50 random `kid`s cost **one** extra JWKS fetch; key rotation still works; a malformed JWKS is 503; `azp` unset is 503; a bad token 401s before the database is touched. |

Two assertions worth calling out because they are easy to write uselessly:

- **Encryption at rest** reads the raw columns as text and greps for the
  plaintext. Asserting `decrypt(col) == token` only proves the round-trip works;
  it is the *ciphertext* that has to be unreadable.
- **Per-user locks** are pinned by ordering, not by wall-clock. User A's refresh
  is parked inside its own lock while user B's token is demanded and returned; a
  shared lock makes that sequence impossible.

### Frontend

cd frontend && npm test        # 63 passed (7 new in tests/auth-credentials.test.ts)

stubbed `fetch` and asserts on what leaves the browser: the admin secret never
goes to `/auth/login` or `/auth/logout`, still goes to `/portfolio/*` and

## 2. Migration

```bash
cd backend && alembic upgrade head    # 0001 → 0004
alembic upgrade head                  # second run: no-op
alembic current                       # 0004 (head)
```

Verified against local Docker Postgres 16. `0004` adds one nullable column,
`broker_links.redirect_uri`; there are no rows in production to migrate (no
per-user link has ever been stored), and a NULL reads as "unknown redirect",
which makes the next login register a fresh client — the safe direction.

## 3. The live run

Two real Clerk users on the real development instance
(`leading-sheepdog-6215.clerk.accounts.dev`), signed in through the real Clerk
UI in a headless browser, against `api.main.app` under uvicorn with a real
Postgres.

**Why a browser and not the Backend API.** A session token minted through
`POST /v1/sessions/{id}/tokens` carries **no `azp` claim** — there is no origin
behind it — so it cannot answer the question F3 needs answered: does the token a
browser actually gets carry the authorized-party claim the backend now insists
on? It does. Observed claims on a live browser token:

```
header: alg=RS256, kid=ins_…(the instance id), typ=JWT
claims: azp, exp, fva, iat, iss, nbf, sid, sts, sub, v
  iss = https://leading-sheepdog-6215.clerk.accounts.dev
  azp = http://localhost:3113          <- the page origin
  sid = sess_…                          <- session-token evidence
  v   = 2
```

Two facts that cost time and are worth writing down:

- **Clerk session tokens live about a minute.** Mint them immediately before
  use; both users are signed in and both tokens minted back-to-back at the end
  of one Playwright run.
- **A new device triggers an email code.** Use Clerk's `+clerk_test` addresses
  (`f3alpha+clerk_test@example.com`), whose code is always `424242` on a
  development instance.
- **`clerkMiddleware()` needs `CLERK_SECRET_KEY` at runtime**, server-side, or
  every route 500s. That is a frontend-hosting requirement for L1, separate from
  the backend, which still holds no Clerk secret for token verification.

### The 24 checks, all passing

| # | Check |
|---|---|
| 1 | anonymous `/auth/status` names nobody |
| 2 | a garbage token is 401 |
| 3 | a Backend-API-minted token (no `azp`) is rejected |
| 4 | user A is identified by their real Clerk token |
| 5 | A's sign-in adopted the pre-F3 `"local"` snapshot day |
| 6 | user B is identified separately |
| 7 | B's sign-in adopted nothing (wrong email) |
| 8 | `/auth/login` refuses the admin header |
| 9 | A completed the full OAuth dance (authorize → callback → link) |
| 10 | A is now linked (`source: oauth`) |
| 11 | B is **not** linked by A's link |
| 12 | a replayed `state` links nothing |
| 13 | a forged `state` links nothing |
| 14 | no plaintext token in the raw columns |
| 15 | the client id and its redirect URI are recorded |
| 16 | a re-link reuses the registered client (registrations unchanged) |
| 17 | both scopes are requested |
| 18 | `/portfolio/summary` is scoped to the caller (A ≠ B) |
| 19 | the interim admin path follows the operator after adoption |
| 20 | `/portfolio/summary` with no credential is 401 |
| 21 | a bad token does not fall through to the admin path |
| 22 | unlink revokes upstream **before** deleting |
| 23 | and the row is gone |
| 24 | (all of the above with `ALPHADESK_SINGLE_TENANT` unset) |

**The live run found a real bug.** Checks 5 and 7 failed on the first pass:
`/auth/status` — the first call a freshly signed-in browser makes — was reading
the token without inserting the `users` row or running adoption, so the
operator's history stayed under `"local"` forever. All four authenticated entry
points now go through `deps.register_identity`, and the regression is pinned by
`test_auth_status_registers_the_identity_too`. No unit test would have caught
it; the suite drove the endpoints in a different order.

### Reproducing it

Everything lived in the session scratchpad (deliberately outside the repo — the
scripts hold real user ids and read the operator's key files). The shape:

1. local Postgres on `:5433`, `alembic upgrade head`
2. a small FastAPI app serving mock IND Money OAuth endpoints on `:8020`
3. the frontend built with `NEXT_PUBLIC_AUTH_ENABLED=true` + the real
   publishable key, served on `:3113` with `CLERK_SECRET_KEY` in the environment
4. the backend on `:8011` with `CLERK_JWKS_URL` / `CLERK_ISSUER` from the
   operator's env, `CLERK_AUTHORIZED_PARTIES=http://localhost:3113`,
   `ALPHADESK_OPERATOR_EMAIL=f3alpha+clerk_test@example.com`,
   `IND_MONEY_MCP_URL=http://127.0.0.1:8020/mcp`, `DATABASE_URL` pointed at the
   **local** container and never at Neon
5. Playwright signs both users in and mints both tokens
6. the checks above run immediately, inside the token lifetime

Restart the backend between runs: adoption caches "already done" per process, so
a re-seeded `"local"` row is (correctly) not adopted a second time.

Two throwaway users remain on the development instance —
`f3alpha+clerk_test@example.com` and `f3bravo+clerk_test@example.com`. Delete
them from the Clerk Dashboard whenever convenient; two earlier ones created
without `+clerk_test` were already deleted.

## 6. Morning checklist — the real-account run

Do these in order once you are awake. Nothing here is optional before L1.

**a. Set the three new environment variables.** Locally (`backend/.env`) and on
the HF Space:

| Variable | Value | Why |
|---|---|---|
| `TOKEN_ENCRYPTION_KEY` | `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` | **Currently unset in `backend/.env` and probably on the Space.** F3 is the first card that stores an encrypted credential, so without it the very first link attempt fails. Losing or rotating it makes every stored link undecryptable (users re-link). |
| `CLERK_AUTHORIZED_PARTIES` | the frontend origins, comma-separated — `http://localhost:3000` locally, the Vercel origin on the Space | Now **mandatory**: unset answers 503 at auth time. |
| `ALPHADESK_OPERATOR_EMAIL` | your Clerk email | Adoption of the pre-F3 `"local"` rows runs only for this address. Unset ⇒ it never runs, and your snapshot history stays under `"local"`. |
| `CLERK_SECRET_KEY` | from the Clerk Dashboard | Only used to resolve your verified primary email for the line above. Without it adoption cannot identify you and will not run. |

**b. Run the migration** against Neon: `cd backend && alembic upgrade head`
(0003 → 0004; one nullable column).

**c. Re-link IND Money — this is the actual test.** Sign in (or, while the flag
is off, use the admin header), then:

```bash
curl -s -X POST https://<backend>/auth/login \
  -H "x-alphadesk-admin-secret: $ALPHADESK_ADMIN_SECRET"     # ← 401 now, by design
```

That call is **JWT-only** as of this card. On the Space, with sign-in off, the
straightforward path is:

1. run the backend locally with `ALPHADESK_SINGLE_TENANT=1` and the Neon
   `DATABASE_URL`, `POST /auth/login` with no auth (links as `"local"`), open the
   URL, complete the IND Money login; **or**
2. build the frontend locally with `NEXT_PUBLIC_AUTH_ENABLED=true` and the real
   Clerk keys, sign in as yourself, and press Connect — which also exercises
   adoption on your real account.

Option 2 is the one that verifies what this card claims. Option 1 leaves the row
under `"local"`, which adoption will pick up the first time you sign in.

**d. Then check, in order:**

- `GET /auth/status` with your session → `authenticated: true`, `source: oauth`,
  `user_id` = your Clerk id.
- `GET /portfolio/summary` → your real totals, `user_id` = your Clerk id,
  `link_health: "linked"`.
- **Restart the backend and repeat.** This is the whole point: pre-F3 the link
  lived in a file inside the container and did not survive a restart. It must
  now come back from `broker_links`.
- Check the scope the vendor actually granted. We request
  `portfolio:read market:read`; C2 saw a `portfolio:read`-only grant come back
  from `/register`. If the token response's `scope` is narrower than requested,
  say so — the research pipeline needs `market:read`.
- `POST /internal/snapshot` with `x-cron-secret` → `users_captured: 1`, and the
  captured row is under your Clerk id, not `"local"`.
- Confirm the pre-F3 history moved: `/portfolio/history` should still show every
  day S1 captured. **If it is empty, stop** — `ALPHADESK_OPERATOR_EMAIL` or
  `CLERK_SECRET_KEY` was wrong, and the rows are still under `"local"` (nothing
  is lost; fix the variable and sign in again).

**e. Unlink once, deliberately**, and confirm the response says
`revoked_upstream: true`. That proves the vendor's `revocation_endpoint`
accepts our call — the only part of §4 that a mock cannot establish. Then
re-link.
